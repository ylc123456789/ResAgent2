# 设计原则

Agent 系统的核心价值，是更好地驾驭和拓展 LLM 的能力。ResAgent2 的架构、工具、上下文和工程机制都应服务于这个目标：让模型更专注地理解任务、取得信息、作出判断并完成工作。

本文先列出全部核心原则，再逐条解释其理由和在 ResAgent2 中的落实方式。这些原则总结本项目的开发经验，也可供同类 Agent 系统参考。具体模块、字段和算法分别查阅 [ARCHITECTURE](ARCHITECTURE.md)、[CONTRACTS](CONTRACTS.md) 和 [CONTEXT](CONTEXT.md)。

## 核心原则一览

| 原则 | 核心思想 |
| --- | --- |
| [1. 围绕 LLM 构建系统，释放模型能力](#llm-first) | 让模型负责理解和判断，让固定代码提供能力、执行操作并检查确定性约束。 |
| [2. 每个 Agent 专注一条主线任务](#layered-autonomy) | 通过分工和上下文隔离减少无关细节，让各层保留完成本职工作的自主性。 |
| [3. 正向准确传递意图，反向尽量保真](#faithful-handoffs) | 正向需要翻译需求，反向尽量直接交还结果，减少多余处理造成的损失和扭曲。 |
| [4. 统一调用、输入输出和业务方式](#unified-agent-io) | 统一协作接口，具体怎样工作由任务输入和模型判断决定，不另设工作模式。 |
| [5. 用工具调用统一模型动作和上下文](#tool-actions) | 读取、执行、问用户、委托工作都是能力调用，使用共同的交互和上下文框架。 |
| [6. 渐进式披露，按需取得原始信息](#progressive-disclosure) | 先提供清晰完整的材料索引，再由模型通过工具读取需要的内容。 |
| [7. 事实有明确来源，判断有可追溯依据](#trusted-facts) | 区分执行事实、材料、展示视图和模型判断，让控制与恢复建立在真实记录上。 |
| [8. 用经典软件工程原则支持维护和扩展](#engineering) | 明确职责、依赖接口、注入实现、复用共同机制，控制变化影响范围。 |
| [9. 实现简洁通用，避免过度设计](#simplicity) | 沿已有路径解决真实问题，抽象来自实际复用需求，不为假想需求增加结构。 |
| [10. 用证据推动改动，以实际效果评价设计](#evidence-driven) | 改动依据实测问题或可靠的外部经验，并验证它是否改善本项目。 |
| [11. 持续积累经验，保持文档与实现同步](#maintenance) | 把稳定原则、当前实现和阶段记录分开维护，让经验能指导后续开发。 |

## 1. 围绕 LLM 构建系统，释放模型能力

### 原则与理由

LLM 是 Agent 系统理解、推理和决策的核心。系统应为它提供清楚的目标、有效的信息、可用的工具和可靠的反馈，帮助它把能力转化为实际工作成果。

随着模型能力增强，架构应允许模型承担更多适合它的工作，而不是把解决问题的路径固化在代码里。判断分工时，关键是这一步需要什么能力：涉及含义、意图、因果、专业推理和策略选择，交给对应的 LLM；能由明确事实直接确定的操作、状态和约束，交给固定代码。

这也意味着模型与代码各自保持边界。授权、预算、身份、文件完整性和操作执行由代码保障；研究材料意味着什么、是否足够、下一步做什么，由模型判断。可靠的执行边界是模型自主工作的基础。

### 在 ResAgent2 中

Scientific 根据用户目标判断需要什么工作和证据，Coding 与 Experiment 处理各自领域的理解、实施和诊断，Compiler 将自然语言工作需求翻译成任务草图。Scheduler、Registry 等固定代码负责调度、登记和事实检查；Interpreter 固定组织已有结果。

例如，文献检索、联网搜索、阅读材料和委托实验的顺序由 Scientific 决定，没有固定研究流水线。模型出现反复无效操作时，先检查指令、可见信息和工具反馈是否完整，再决定如何修正，避免靠不断追加特殊规则代替模型判断。

**修改时问自己：这项机制是在帮助模型完成任务，还是把模型本可承担的判断写死了？**

## 2. 每个 Agent 专注一条主线任务

### 原则与理由

分工的目的，是让每个 Agent 把注意力集中在自己的主线任务上。研究判断、代码实施和实验执行需要不同的信息；把全部实施过程留在主 Agent 的上下文中，会增加无关细节、拉长历史，并干扰主线判断。

主 Agent 交付目标、材料和约束，专业 Agent 自主完成具体工作，再交回结果、解释与依据。上下文隔离不等于信息隔断：原需求要传下去，有用结果要交回来，必要原件要可读取。一个任务内部的准备、检查和执行仍可以连续完成，无需把每个小步骤拆成新 Agent 或新任务。

### 在 ResAgent2 中

可以把系统理解为一个协作的整体：

| 比喻 | 对应部分 | 主线职责 |
| --- | --- | --- |
| 大脑 | Scientific Agent | 围绕用户研究目标作科学判断，决定还需要什么材料和工作 |
| 神经系统 | Compiler、Interpreter | Compiler 将研究意图传到执行层；Interpreter 将执行结果交回研究层 |
| 器官 | Coding、Experiment Agent | 分别完成代码工作和研究实验，交付专业结果 |

Controller 管理整次研究往返，Scheduler 推进已接受的任务图；它们支持上述分工。这个比喻解释设计目的，具体职责仍以[架构](ARCHITECTURE.md#overview)为准。

Scientific 的 Session 跨研究回合复用；Coding、Experiment 的 Session 按 Task/Attempt 隔离。Scientific 通过报告和工件取得下游结果，任务 Agent 的完整实施历史留在各自 Session 中。每个 Agent 得到完成自己任务所需的指令和材料，并在授权与预算内选择具体工具步骤。

**修改时问自己：是否让某个 Agent 承担了偏离主线的职责，或接收了本不需要的实施细节？**

<a id="faithful-handoffs"></a>

## 3. 正向准确传递意图，反向尽量保真

### 原则与理由

向下提出工作与向上交回结果，解决的问题不同。正向链路需要把目标、约束和证据需求翻译为可执行工作；反向链路应尽量把专业 Agent 的结果直接交回主 Agent，让主 Agent 自己理解其意义。

每增加一次摘要、转述或重新解释，都可能丢失细节或改变原意。因此，反向链路以近乎无损地交还结果为目标，优先保留原报告、原始产物及失败和局限，只做必要的组织与导航。架构不追求形式上的完美对称，不要求两个方向有相同的处理层或模型调用次数。

保真也不等于把所有原始内容一次性塞入主 Agent。可以先呈现结构事实和适量正文，只要省略明确、原件完整保存、后续可按需读取，就能兼顾信息保留和上下文效率。

<a id="interpreter-current"></a>

### 在 ResAgent2 中

```text
正向：Scientific 提出目标与证据需求 → Compiler 翻译 → Coding / Experiment 执行
反向：执行报告与工件 → Interpreter 固定组织 → Scientific 阅读并作科学判断
```

Compiler 使用 LLM 翻译需求，固定代码分配身份、检查结构；Interpreter 不再调用 LLM 二次改写报告，而是按已有任务和尝试组织最新已记录的报告原文、状态、错误和工件入口。

Controller 冻结工作记录和反馈；Scientific 先看到完整目录、必要事实与按容量展示的报告。原报告、历史尝试和原始产物仍可读取。这里保证交接减少转述损失，不承诺所有正文始终完整出现在模型输入中，也不把专业报告当成无误的测量。取舍见 [ADR-0020](../history/decisions/0020-deterministic-work-interpreter.md)。

**修改时问自己：新增交接步骤是否必要，是否改变了目标或结果的原意，原件是否仍能追溯？**

## 4. 统一调用、输入输出和业务方式

### 原则与理由

统一协作接口可以降低组织和编排的复杂度，让不同 Agent 能沿相同方式接收任务、交付成果、暂停和恢复，也为后续替换实现或优化系统提供稳定基础。

任务内容以自然语言和材料表达，必要的身份、权限、预算、状态等以控制字段表达。Agent 根据输入和模型判断决定如何工作，分析、修改、执行等不需要变成几种显式业务模式。统一接口并不要求所有 Agent 的专业能力相同。

### 在 ResAgent2 中

三个 Agent 都使用 `invoke(AgentRequest) → AgentResult`。业务输入为 `instruction + input_artifacts`，业务输出为 `report + artifacts`；其余字段承载必要控制。上游通过公共结果、SessionRef 和工件协作，不读取下游私有 memory 来驱动流程。

Coding 可以分析现有代码，也可以修改和验证；Experiment 可以解释已有结果，也可以执行新实验。具体行为由任务决定，可写权限不要求必须修改。回答问题后仍沿同一调用继续原工作，失败重试才创建独立 Attempt；新尝试不自动继承旧问答，必要时重新询问。详见[统一调用契约](CONTRACTS.md#module)。

**修改时问自己：是否可以沿统一接口表达需求，新增模式或专用输入输出是否真的必要？**

<a id="tool-actions"></a>

## 5. 用工具调用统一模型动作和上下文

### 原则与理由

模型通过调用能力与外部系统交互。文件读取、命令执行、搜索、向用户提问和委托工作都可以看成工具调用：提出动作，接收回执，再依据结果决定下一步。

共同的交互形式让模型更容易理解“做了什么、返回了什么、现在怎样继续”，也让运行时统一处理记录、反馈和协议历史。统一的是交互框架；不同能力仍需保留自己的状态、授权和执行责任。发出问题或工作申请，不代表答案或执行结果已经得到。

### 在 ResAgent2 中

三个 Agent 共用仅使用原生 function call 的 AgentLoop，模型可用工具由实际注册的 Tool 定义，不另维护动作名清单。`ask_user`、`finish` 和 Scientific 的 `request_work` 都通过工具协议表达；`request_work` 不另建一套模型动作格式，跨 Agent 执行由 Controller 接管。

模型上下文也使用共同的四部分：

1. **固定契约**：职责、系统规则、工具说明与 schema。
2. **任务需求**：当前指令与本作用域累计的业务问答；操作批准不作为任务需求累计。
3. **原生协议历史**：成对保存的 assistant/tool 调用与回执。
4. **当前任务上下文与完整工件索引**：当前事实、反馈、可见材料片段和导航目录。

每轮从当前事实重建业务上下文，协议历史保留完整回合。必要时压缩较早历史在模型输入中的投影，原始事件保留。这样既支持原生 function call 的连续性，也让当前任务和材料不依赖旧摘要恢复。Compiler 是无状态编译，Interpreter 不调用模型，不强行套用 Agent 的 Session 框架。细节见 [CONTEXT](CONTEXT.md#basics)。

**修改时问自己：新动作能否进入已有工具与上下文框架，调用回执与后续真实结果是否分清？**

<a id="progressive-disclosure"></a>

## 6. 渐进式披露，按需取得原始信息

### 原则与理由

上下文应先帮助模型判断有哪些信息值得读，再提供需要的内容。大量文件、论文、网页和日志应持久保存，通过索引、简短说明和读取工具供模型按需取得。

渐进式披露的核心是让材料可发现、可定位、可继续读取。索引说明“有什么”，预览帮助决定“读什么”，正文提供“具体写了什么”。它们的职责不同；缩短预览不能删除原件，历史压缩也不能让已知材料从目录中消失。

### 在 ResAgent2 中

本轮授权输入与 Session 中已登记工具产物合并为唯一、完整的 `artifact_index`；索引保留 ID、类型、说明和必要来源关系。这里的完整范围是当前 Agent 可用的材料，不是整个 Run 的所有内部记录。

文献搜索返回论文元信息和摘要预览，网页搜索返回来源预览；完整结果保存为工件。获取论文全文或网页正文是另外的工具调用，会登记新工件并更新索引。`read_artifact` 按范围返回内容，不创建新的正文工件；文件和工件的已读片段形成有界工作集。

完整目录和必需输入不静默截断，放不下时明确报告容量问题。正文可按需分段读取，当前工作集可选择片段，原件和读取事件仍保留。具体接入方式见[文献与网页上下文](CONTEXT.md#literature)。

**修改时问自己：模型是否知道材料在哪里，能否按需读到原文，是否把不必要的大段正文提前塞入了上下文？**

## 7. 事实有明确来源，判断有可追溯依据

### 原则与理由

模型需要可信的执行反馈才能正确判断。每项状态和事实应有明确的权威来源；目录、摘要和提示词从这些记录生成，不能再维护另一份可独立漂移的事实。

材料保存、内容读取、实际执行和结论成立也是不同事实。文件存在不说明操作成功，读取过不说明支持结论，流程完成不说明假设成立。代码保存和检查可确定的事实，模型解释含义并说明依据与局限。

执行约束应在代码中可靠生效。审批、预算、暂停和恢复建立在身份与真实记录上，才能让自主操作可控、可继续。失败、负结果和未知状态同样是信息，应如实保留。

### 在 ResAgent2 中

Controller 管 Run 与研究往返，Scheduler 管 Task/Attempt，Agent 与 Runtime 管 Session。Registry 校验并冻结候选材料，`Run.artifacts` 保存登记结果；ResearchIndex 和模型索引是派生导航，不另存路径、hash 或权限权威。

Agent 的领域完成检查、接收端的来源冻结和 Run 最终交付检查分别承担不同责任；同一事实规则复用已有 helper。科学观点由 Scientific 判断，`inconclusive` 或负结果也可以合法完成研究。

已有执行机制遵守以下规则，具体协议见[契约](CONTRACTS.md)：

- 内部调用共享 Run 的用量、期限和授权，只能继承或收紧，暂停恢复不重置已有消耗。
- 批准绑定准确操作并在执行前消费；问答继续原任务和会话，结果未知的副作用不自动重放。
- 错误回执必须合法保存，正常失败与中断分清；可选 trace 失败不覆盖业务结果，权威状态保存失败不能吞掉。

这些规则的通用经验是明确事实、控制和诊断的责任边界。当前单 Run 单写入者、应用层权限、跨文件保存等实现边界见[状态与恢复](ARCHITECTURE.md#state)，不能据此承诺 OS 沙箱、共同事务或所有副作用恰好执行一次。

**修改时问自己：这项事实由谁产生和保存，模型看到的是事实还是展示，失败与恢复是否仍能追溯？**

## 8. 用经典软件工程原则支持维护和扩展

### 原则与理由

Agent 系统仍是软件系统。职责分离、依赖倒置、开闭原则和共享机制的价值，在于减少修改波及范围，使代码便于理解、测试、替换和维护。

模块通过公共接口合作，由外层入口选择具体实现；扩展能力优先沿既有接口。共同的运行机制共享，专业判断和领域规则留在所属模块。是否引入接口或抽象，应看是否存在稳定的调用边界或实际替换需求。

### 在 ResAgent2 中

Scheduler 依赖 `ModulePort`，CLI 的统一组合根注入具体 Agent，真实 E2E 复用这一装配；Orchestrator 不 import 具体 Agent 实现。三个 Agent 共用 AgentLoop，通过 `AgentDefinition` 注入提示词、工具、上下文、权限策略和完成检查。

Capabilities 提供模型工具入口，Components 提供普通操作与共享呈现；二者不必逐项配对。内部固定操作可以直接使用组件，专业工具可以复用同一执行部件。新增普通工具通常只需调整工具、输入 schema 和所属 Agent 的装配，无需复制核心循环；公共契约变化则同步生产者、校验、存储和消费者。

模块独立不要求零依赖、每类一个包或单独部署；开闭原则也不意味着核心代码永远不改。实际依赖与扩展边界见[模块边界](ARCHITECTURE.md#modules)。

**修改时问自己：变化是否集中在职责所属位置，调用方是否依赖约定，共同机制是否出现了第二套实现？**

<a id="simplicity"></a>

## 9. 实现简洁通用，避免过度设计

### 原则与理由

好的实现用清楚、少量的机制解决实际问题。简洁是减少概念、状态和执行路径，通用是在真实共性上复用；两者都以读者和维护者能理解行为为基础。

抽象应来自明确的共同语义与复用需要。对未来的设想可以记录，但不要提前建立管理器、插件层、业务模式或兼容框架。同样，不能为了减少几行代码，把表面相似、责任不同的行为合成一个难懂的通用系统。

校验和防御应对应真实边界与可处理后果。外部输入、供应商响应和变化中的文件需要检查；内部已成立的事实不应层层猜测、宽泛捕获后用默认值掩盖错误。

### 在 ResAgent2 中

修复优先沿已有生产路径：删除死代码、纠正权威来源、复用现成函数或补小型 helper。截断边界问题留在截断函数，网页代码块空白问题留在解析器，trace 写盘共用小函数；这些问题无需新增控制层或合并不同模型协议。

接口清理同步删除无消费者字段和旧逻辑，保持一条生产主线。当前不保留已被取代协议的兼容层；不兼容的旧 Run/Session 明确拒绝恢复，原记录保留。不同职责的验证仍可以存在，同一事实实现再共享。

**修改时问自己：能否用已有组件和更少概念解决问题，新增抽象是否有真实使用者和明确收益？**

<a id="evidence-driven"></a>

## 10. 用证据推动改动，以实际效果评价设计

### 原则与理由

改动应有具体问题、实验数据或可靠外部经验支撑。论文、公开技术文档和成熟项目经验可以提供候选方法；本项目的复现、测试和质量对照用来判断方法是否适用。不能因为设计看起来更新、更统一或更复杂，就默认它会改善 Agent。

不同证据支持不同结论。代码测试可以证明接口与边界正确，真实任务可以展示模型在某次运行中的表现，成对对照更适合评价修改前后的质量差异。一次完成不能推出普遍提升，外部项目成功也不能直接证明本项目受益。

验证应与改动风险和主张相称：确定性 bug 用复现与边界测试核对；影响模型决策、材料利用或科研交付的变化，再用相应真实任务和必要对照评价。

### 在 ResAgent2 中

提出修改前，沿“入口 → 信息或执行路径 → 断点 → 实际后果”确认问题，同时查已有组件、历史决定和公开实现。说明预期改变什么，以及用什么证据判定有效。

确定性测试检查实际长度、集合完整性、身份配对、冻结内容和持久恢复；mock E2E 检查公开入口的模块组合；真实材料验收和 L3 检查指定任务中的材料利用与科研交付。质量主张限制在实际测过的条件内。

验收基准来自真实来源、冻结原件或独立复算。差异出现时核对产品、来源和测试方法，保留失败与更正理由；不修改被测产物或放宽断言来获得通过。验证入口见[开发与验证](../guides/DEVELOPMENT.md#local-checks)。

**修改时问自己：问题和方案分别有什么依据，验证是否测到了所声称的改善，收益是否值得新增复杂度？**

<a id="maintenance"></a>

## 11. 持续积累经验，保持文档与实现同步

### 原则与理由

经验应转化为能复用的理由、原则和方法，而不只是一串修改记录。文档需要让后续开发者理解“为什么这样设计”，同时分清当前行为、历史取舍和尚未实施的想法。

稳定原则与具体实现分开维护，才能在实现变化时保留有价值的指导思想，也避免把某次临时方案提升为永久规范。原则可以演进，但需要说明新的依据和取代关系。

### 在 ResAgent2 中

本文维护指导思想与开发方法；ARCHITECTURE 说明模块与流程，CONTEXT 说明模型输入，CONTRACTS 定义接口与接收规则。字段表、预算数值、供应商差异和运行轮次由相应文档维护，不在原则中反复复制。

重要取舍记入 ADR，阶段计划、审查和验收保留在 history。代码行为变化时同步当前说明与受影响示例；计划不当作已有能力，历史中的“当前”只对记录时点有效。原则是否落实，要能沿代码、接口与验证证据检查。

**修改时问自己：读者能否分清设计理由与当前行为，文档是否与实际生产路径一致，经验是否可指导下一次决策？**

## 开发与评审时怎样使用这些原则

先明确用户目标和实际问题，再决定改动。评审至少回答：

1. 由模型还是代码处理，职责和上下文是否放在合适位置？
2. 目标能否准确传下去，结果能否保真交回来，材料能否按需读取？
3. 能否沿统一接口和已有机制完成，新增复杂度是否必要？
4. 事实、授权、失败和恢复是否连贯，生产者到消费者是否全部接通？
5. 问题与方案有什么依据，验证覆盖什么，哪些文档需要同步？

这些问题用于落实前面的原则，不构成另一套架构或审批流程。
