# L3 测试、外部基准与自进化：调研记录

日期：2026-09-15。性质：资料核对与开发建议，**不是新架构规范，也不是外部基准已接入/跑通的报告**。本轮不安装这些项目、不下载大型数据、不启动优化器。实际测试规程见 [L3 风格测试](L3_RESEARCH_TEST_2026-09-16.md)。

## 1. 先说结论

ResAgent2 现在更需要一组可信、可反复使用的真实任务，而不是再抽象一个“支持所有自进化算法”的框架。

能做优化不等于底座已经完美：只要能固定一版系统、执行任务、保留轨迹并判断结果，就能研究局部改进。研究的优化对象本身经常包括 prompt、工具说明、上下文选择和工作流。应区分“为了本次对照实验固定接口”与“业界已经找到了通用最佳接口”。

我们的建议是：先完成一个 L3 案例，再选择少量公开任务形成开发集/独立验收集。以后若研究优化，每次只放开一个改动面；先得到可信比较，再谈自动继承。这个顺序是针对本项目的判断，不是论文已证明的通用路线。

## 2. “数据集”要分成两种

- **实验数据**：例如 CIFAR-10，是被实验模型训练/评估的数据。
- **Agent 评测任务集**：包含问题、初始代码/数据、权限与资源边界、评分办法；测的是 Agent 能不能完成研究工作。

给 ResAgent2 加 CIFAR 数据不能直接得到 Agent benchmark。反过来，一个 benchmark 常常要下载多个任务各自的数据和环境，不能因代码开源就认为数据免费、可再分发或单卡可跑。

## 3. 有哪些能借用的基准

下面是读取官方仓库/论文后的范围判断；具体使用时仍需锁定版本、选择任务、核对数据许可与硬件。没有一个名称可以直接替代我们的全链验收。

| 基准 | 覆盖的工作 | 值得借的部分 | 当前适合程度与边界 |
|---|---|---|---|
| [MLRC-Bench](https://github.com/yunx-z/MLRC-Bench) | 7 个 ML 研究竞赛任务，提出方法并修改真实代码 | starter code、dev/test 隔离、独立 evaluator、同一执行入口 | 最值得优先检查；需要逐任务配置环境，部分数据要 Kaggle 授权，不是零准备 |
| [ResearchBench](https://github.com/ankitala/ResearchBench) | 文献启发检索、假设组合、假设排序 | 固定候选池与 tiny 子集，便于单独测 Scientific 的研究前半程 | 文本侧较轻；不执行实验，得分不能代表完整科研能力。代码 MIT，数据 [CC BY-NC 4.0 与上游条款](https://github.com/ankitala/ResearchBench/blob/main/DATA_LICENSE.md) 另算 |
| [ScienceAgentBench](https://github.com/OSU-NLP-Group/ScienceAgentBench) | 102 个跨学科数据驱动任务，生成并执行科学分析程序 | 明确输入/产物检查、跨领域任务、按实例选小子集 | 后续可补广度；异构依赖与数据需逐项预检，采用官方建议的 verified split；部分评估依赖模型 judge |
| [MLAgentBench](https://github.com/snap-stanford/MLAgentBench) | 13 个任务里的读取、编辑、实验迭代与改进基线 | 已有 starter/evaluator、执行日志与工作区记录 | 可挑 CIFAR 等单任务；旧环境与上游数据需要适配，不机械照搬“必须提升某百分比”的通过线 |
| [MLE-bench](https://github.com/openai/mle-bench/) | 75 个 Kaggle 竞赛，训练、迭代并提交结果 | 独立 grader、真实工程交付、任务隔离 | 全量很重，官方 Lite 也不是“小下载”；先按单题估算存储、算力与许可，不作为当前第一步 |
| [PaperBench](https://github.com/openai/frontier-evals/blob/main/project/paperbench/README.md) | 20 篇论文的代码实现与实验复现 | 将代码存在、实际执行、结果匹配分开验收 | 高成本；Code-Dev 不执行实验，不能拿它代替完整 L3。官方文档是协议/成本依据，本文未实跑 |

再补一个定位不同的选择：[CORE-Bench](https://github.com/siegelz/core-bench) 更偏给定科研仓库的计算复现，可用于定位环境/执行问题，不直接检验新方法选择。

### 现在只借两件事

1. **从 MLRC-Bench 借实验边界**：可改的方法代码与不可改的评分器分开，开发阶段不能看到测试答案。官方仓库明确规定 env 与隐藏 test 文件的区别，并要求评价代码只读。不要把其 starter/评测资料全塞进 Agent 工作区。
2. **从 ResearchBench 借文献诊断样本**：需要稳定定位检索/选择问题时，用固定论文候选池单独测试；与实时 arXiv 可用性测试分开报告。它有 12 条 tiny smoke 子集，无需先跑完整研究流程。

先写的 L3 调度案例沿用我们熟悉的 CIFAR 资源，更适合观察长链行为；MLRC-Bench 则是下一步减少自建任务/评分成本的来源。两者不是同一个榜单：改过目标、工具、预算、数据或评分，就必须称为“改编任务”，不能直接比较官方分数。

引入某题前做一张简短清单即可：任务版本/许可、下载量、算力、初始文件、允许修改范围、运行命令、评分器位置、开发/测试隔离。**不需要先发明 benchmark registry 或新任务 DSL。**

## 4. 截图里的论文是什么

已核实官方条目：[The Last AI Built by Humans: Toward Genuine Recursive Self-Improvement](https://arxiv.org/abs/2609.11873)，arXiv **2609.11873v1**，2026-09-10；本次读取了 [HTML 正文](https://arxiv.org/html/2609.11873)，不是仅凭截图或标题判断。

它主要提供综述、自治路线图与初步实证，不是一个已经实现完整 RSI 的统一系统。五级大意是：执行人指定的改进 → 自选改进策略 → 自选下一轮学习经验 → 根据部署经验适应 → 改进“改进机制”并让后继继承。Theseus 部分的环境整理实验仍是早期阶段，不能等同于完整递归循环已建立。这里的等级与我们项目的 L3 测试命名无关。[原文 §1.4、§5.1、§6](https://arxiv.org/html/2609.11873)

## 5. 他们到底怎么实现优化

不用把“自进化”先想成模型自己训练自己。下面几个可读源码的例子，很多是让固定模型去搜索更好的程序或提示：

| 项目 | 放开让系统改什么 | 如何判断改得更好 | 并没有随意放开的东西 |
|---|---|---|---|
| [GEPA](https://github.com/gepa-ai/gepa) / [论文](https://arxiv.org/abs/2507.19457) | 原始研究主要是 prompt；当前实现也可优化文本化代码/配置 | 读取执行轨迹、反思失败、生成候选，以任务 metric 和候选集合选择 | 调用方仍需提供 evaluator、数据与评估预算；不是自己宣布成功 |
| [ADAS](https://github.com/ShengranHu/ADAS) / [论文](https://arxiv.org/abs/2408.08435) | 以 Python 表示的 Agent 实现，包含 prompt 与调用组织 | meta-agent 参考历史候选与成绩，生成新实现，再在验证数据上运行 | 基础调用 API、任务数据、评分过程和搜索预算由实验者提供 |
| [Darwin Gödel Machine](https://github.com/jennyzzt/dgm) / [论文](https://arxiv.org/abs/2505.22954) | Coding Agent 自身代码，例如工具、工作流和上下文管理 | 执行 coding benchmark，保留候选/分支，选父代继续修改 | 原研究不更新基础模型权重；候选归档、父代选择与外部评测不等于都能自改 |

一个便于理解的共性抽象（我们的归纳，不是三个项目完全相同的实现）：

```text
固定任务与评分边界
    → 执行当前版本，保存轨迹/结果
    → 找失败原因，生成一个候选改动
    → 相同预算重新评估
    → 保留有效改动，或拒绝/回滚
    → 下一轮使用保留下来的版本
```

例如 GEPA 的公开接口让调用方交入 seed candidate 和 evaluator：优化器负责搜索，evaluator 负责告诉它任务表现如何。这个边界可以很小，不必先搭一套分布式 Agent 平台。DGM 甚至直接改工具与上下文相关代码，恰好说明它们并非已经定型的底层答案。

“优化器看见了错误轨迹”不保证它找对根因；“验证集更高”也不保证泛化更好。反复查看同一评价器、更多计算量、模型 judge 偏差和继承坏规则都可能造成假进步。这是为什么我们应把可改代码/提示与独立测试、资源限制、合入决定分开。

## 6. 对 ResAgent2 的具体启发

当前已有的资产——清楚的模块入口、持久 Run/Session、实际工件、full trace、有界失败恢复——足够开始做**可比较的实验**，不必等一个想象中的完美底座。但“足够开始”不代表后续不会发现接口/上下文缺口。

建议顺序：

1. 按 L3 规程跑一次，先区分资源/外部服务、模型、上下文、实现、评价各层失败，不把所有失败都叫漂移。
2. 留下少量不同类型的任务，固定输入、配置、结果检查与预算；把常用开发任务和独立验收任务分开。只有一题时，先称案例研究。
3. 先人工做单变量改进对照，例如只改一个 Agent 的 prompt 或一类工具结果呈现，保留负结果和费用。没有收益就不合入。
4. 确认评价可靠后，才考虑让类似 GEPA 的优化器提建议；初版可继续人工验收/合入，不让系统直接修改 main、评分器或凭据权限。

无需现在新增 self-evolution Agent、记忆数据库、插件抽象或新的优化专用 Contract。以后真接优化器，再围绕已经可运行的“输入任务 → 跑一版 → 返回分数与证据”写最薄的一层连接即可。
