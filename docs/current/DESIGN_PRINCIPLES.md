# 设计原则与开发方法

ResAgent2 的目标是让 LLM 在明确的职责、可靠的工具和可追溯的材料支持下完成研究任务。设计的重点是帮助模型理解目标、取得证据并作出判断，同时让代码可靠地执行、记录和约束操作。

本文沉淀设计理由和开发方法。它既指导本项目后续开发，也可供类似 Agent 系统参考；具体接口、字段和数值以当前实现文档为准。原则不能作为顺便重构代码的理由，设计目标也不等于已经验证的能力。

| --- | --- |
| 为什么这样分工，修改时怎样取舍 | 本文 |
| 模块怎样协作，一次研究怎样运行 | [ARCHITECTURE](ARCHITECTURE.md) |
| 模型每次收到什么，材料如何进入上下文 | [CONTEXT](CONTEXT.md) |
| 请求、结果、状态、工件与工具的精确约定 | [CONTRACTS](CONTRACTS.md) |

全文按“总体目标 → 协作边界 → 事实与材料 → 上下文 → 执行与恢复 → 实现与验证”展开。文中的“必须”表示开发约束；“当前边界”表示实现范围，不能靠提示词或文档措辞扩大它。

## 1. 三个总体设计目标

<a id="llm-first"></a>

### 1.1 模型负责理解和判断，代码负责确定事实与执行约束

需要理解含义、意图、因果或专业知识的工作，由职责对应的 LLM 完成。代码负责给它准确的信息，提供可靠操作，并检查可确定的事实和硬约束。

| 问题 | 本项目的分工 |
| --- | --- |
| 研究要解决什么，还缺什么证据，结论是什么 | Scientific 的 LLM |
| 如何把工作需求转成任务及依赖 | Compiler 的 LLM |
| 怎样修改代码、设计实验、解释执行问题 | Coding 或 Experiment 的 LLM |
| 身份是否匹配、路径是否授权、预算是否足够 | 代码检查 |
| 文件内容、退出码、hash、调用用量和实际状态 | 代码取得事实并保存 |
| 怎样把已有执行报告和证据入口交还给 Scientific | Interpreter 用固定代码组织 |

已有角色能承担的语义工作，优先由该角色完成。不要用不断增加的关键词、特例或另一层模型来替代它。结构有效不能证明科学观点正确，模型判断也不能改写执行事实或绕过授权。

**处理问题的方法**：模型反复做无效操作时，先检查任务说明、工具反馈和信息是否到达。例如批准后仍反复列目录，应确认它是否知道批准只允许执行、并不代表执行已经发生。修复信息链，而不是增加“列目录三次后自动操作”的规则。

<a id="layered-autonomy"></a>

### 1.2 职责分层，每层保留完成自己工作的自主性

Scientific 是研究的“大脑”：以用户目标为依据选择工作、获取材料并形成判断。Compiler 翻译工作需求；Controller 管理研究往返；Scheduler 执行已接受的任务图；Coding 和 Experiment 在自己的专业领域完成任务。

上层交付目标、材料和约束，专业 Agent 在授权与预算内选择工具步骤。上层不为所有任务写死操作顺序；下层不接管上层的研究目标和最终科学判断。

这种分工不是以 Agent 数量衡量。只有明确、无法由现有角色承接的职责才值得新增角色。共享机制也不消除专业判断：三个 Agent 可以使用同一个循环，同时拥有不同提示词、工具、权限和完成检查。

### 1.3 向下传递意图，向上返回事实、解释和证据

```text
正向：研究目标与证据需求 → Compiler 翻译为任务 → 专业 Agent 执行
反向：执行事实、报告与证据 → Interpreter 对应原需求组织反馈 → Scientific 综合判断
```

正向保留目标、约束和证据需求。例如“一次实际操作”不能在编译后变成“只允许调用一次工具”。反向保留完成情况、失败、警告、局限和原件入口，不能为了看起来成功而删掉负结果。

交接要让接收者无需读取发送者的私有状态就能继续工作。固定整理不能变成新的测量或新的科学结论；Scientific 负责理解交回材料的意义。

两个方向的职责应完整，但不要求目录结构、类数量或 LLM 调用次数对称。是否调用模型，取决于该环节是否需要语义判断。

<a id="interpreter-current"></a>

**本项目的落点**：Compiler 使用 LLM 生成任务草图，代码分配身份并检查结构；Interpreter 不调用模型、不管理 Session、不修改 Run，只组织已有报告与结构事实。Controller 保存交接结果，Scientific 再作综合判断。详见[研究流程](ARCHITECTURE.md#flow)。

## 2. 通过公共契约协作，共享机制保持稳定

### 2.1 统一表达工作，不增加隐含业务模式

所有 Agent 都使用 `invoke(AgentRequest) → AgentResult`：请求以 `instruction` 和 `input_artifacts` 表达工作，结果以 `report` 和 `artifacts` 交付，另有必要的控制字段。

分析、修改、执行和问答恢复不再建立另一套业务模式。工具可写不等于任务必须修改；工具可执行不等于当前已获执行授权。跨 Agent 交接依靠公共请求、结果、SessionRef 和工件，不直接互调，也不读对方私有 Session 或 memory。

Compiler 的 JSON 请求与 Agent 的原生工具请求是不同底层协议，不是 Agent 的两种业务模式。恢复时保持 Session 的协议身份，不能静默降级或切换协议。详见[统一 Agent IO](CONTRACTS.md#module)。

### 2.2 同一种运行机制只保留一套

本项目的控制职责分为三层：Controller 管研究往返，Scheduler 管任务执行，AgentLoop 管模型与工具的步骤。Compiler 无状态翻译需求，Interpreter 固定组织反馈，两者没有 Agent Session。

Scientific、Coding 和 Experiment 共用 AgentLoop，用 `AgentDefinition` 注入各自的提示词、工具、上下文、权限策略和完成检查。专业差异应在这些明确位置表达，不复制循环，也不向共享循环添加识别具体 Agent 的业务分支。

### 2.3 调用方依赖约定，入口选择实现

Scheduler 只认识 `ModulePort`，不导入具体 Agent；CLI/E2E 入口创建实现并注入。模型、存储、Compiler 和 Interpreter 等可替换能力也沿明确接口装配。

Python `Protocol` 描述接口形状，不要求实现继承同一个基类。可替换实现还必须保持身份、暂停、预算、失败和工件的行为约定，仅有同名方法不够。

独立不等于零依赖、每个类单独一个包或每个模块单独部署。共享 contracts、runtime 和普通组件是明确的依赖。依赖范围由[模块边界](ARCHITECTURE.md#modules)说明和边界测试核实。

### 2.4 工具入口与普通操作分开，但不强制造两层类

Capabilities 是暴露给模型的工具入口；Components 提供普通操作和共享呈现。二者不要求一一对应，也不要求所有内部操作经过工具入口。

例如 `run_shell`、`run_setup` 和 `run_verification` 可共用 ProcessRunner，仍分别保留通用执行、环境安装和验证的记录及约束。内部固定 Git 或环境操作可直接调用普通组件，无需伪装成一次模型工具调用。

## 3. 区分权威事实、工件和派生目录

### 3.1 每项事实有一个明确的权威所有者

Run/WorkRequest、Task/Attempt 和 Session 分别管理自己的状态。授权、资源登记、环境绑定和实际执行结果也各有明确来源。摘要、目录、提示词和缓存不能成为另一份独立的权威状态。

| 层次 | 本项目的例子 | 约束 |
| --- | --- | --- |
| 权威事实 | 持久化的 Run、Task/Attempt、Session、Run.artifacts | 在所属边界更新，保留身份与历史 |
| 派生视图 | ResearchIndex、模型的 artifact_index | 从授权记录重建，引用原身份，不另授权限 |
| 模型输入投影 | 预览、读取片段、历史摘要 | 控制呈现体积，不改变原件与原事件 |

不要从报告措辞推断机器状态，也不要从一个目录字段推断权限。发生冲突时回到所属的权威记录和生产路径核对，不能再加一份状态来“同步”两份错误来源。

### 3.2 工件是交接与追溯对象，不是“科学正确”的认证

模型提交的候选文件还没有成为接收端已登记的工件。Registry 在登记边界检查来源、授权和文件事实，冻结内容并生成 `ArtifactRef`；持久化的 `Run.artifacts` 保存登记结果。

登记工件不代表它有研究价值。搜索结果、论文元信息、网页正文、代码和实验结果可以处在不同材料阶段；是否相关、是否足以支持结论仍需判断。正文是否读过也与登记分开。

工件身份统一生成，来源关系用显式字段保存，不从 ID 或文件名解析含义。跨任务交付用精确的 `output_name` 绑定，不能按相似文件名猜测。详见[工件契约](CONTRACTS.md#artifacts)。

### 3.3 导航、读取和支持结论是不同事实

完整目录告诉模型“有哪些可用材料”，显式读取告诉它“原件写了什么”，引用说明“结论依据在哪里”。三者不能互相替代。

模型索引来自该次调用获授权的输入与已登记工具产物，不等于把整个 Run 的登记表展开到每个 Agent。目录只保留导航所需字段，原件路径、hash 和权限仍由权威记录管理。

“登记”“存在”“返回过内容”和“证据支持结论”是不同事实。访问记录用于追溯，不能自动变成引用、提问或完成资格。摘要不能冒充全文，网页搜索线索不能冒充网页正文，二手引用应说明其层次。

### 3.4 多层校验检查不同责任，不建立重复判决

Agent 检查领域执行与完成事实，登记层检查来源及冻结，接收端和 Run 检查各自的交付要求。这些边界可以同时存在；同一文件事实规则应复用具体 helper，而不是复制实现。

不要把职责不同的校验合成一个全局验证框架。可读、已引用和科学有效性也不能合成单一布尔值。Run 完成说明流程与交付满足约定，不说明假设成立；负结果也可以是成功完成的研究。

## 4. 上下文帮助模型发现、理解和继续工作

### 4.1 协议历史、任务需求和材料目录各有用途

当前统一模型输入以四部分组织：固定契约、任务需求、原生 `assistant/tool` 历史、当前任务上下文及完整工件索引。具体字段和各 Agent 差异看 [CONTEXT](CONTEXT.md#basics)。

初始任务与当前作用域的 `ask_user` 问答保留任务依据；`request_work` 按普通工具处理；工具回执包含说明、inline 内容和工件引用。读取正文不创建第二份正文工件，返回的片段进入工具历史。

成对历史保证原生 function call 能继续，完整索引保证材料在旧回合压缩后仍可发现。历史不能代替目录；目录也不能证明模型读过原件。不要把同一答案、正文或报告反复塞进多个上下文段。

### 4.2 重构和压缩只改变模型输入的投影

每轮根据当前事实重建任务上下文与完整索引，同时保留成对的原生协议历史。历史过长时，用摘要替代较早完整回合在模型输入中的投影；持久化的原始 `tool_turns` 和冻结工件保留。

预览、分页、上下文裁剪和压缩是不同位置的体积控制，不能静默删除原始事件或完整目录。必需内容放不下时明确报告容量问题，不把缺项输入伪装成完整输入。

### 4.3 每个“有界”承诺都要检查实际输出

工具 IO 上限、模型上下文上限、持久化记录上限和供应商限制是不同边界。某一边界通过不能推出其他边界通过，错误应说明真正所属的边界。

测试应验证具体性质，例如实际输出长度不超过预算、目录集合无遗漏、工具调用与回执身份配对、压缩边界不拆开完整回合。只检查配置值或普通尺寸样例不足以证明有界行为。

## 5. 授权、预算、失败与恢复构成同一条执行链

### 5.1 子调用继承约束，不开另一份预算和权限

内部调用只能继承或收紧 Run 的调用余额、期限和授权。三个 Agent、Compiler、重试、纠错、压缩和托管网页搜索共用 Run 模型调用总账；固定 Interpreter 不调用模型。

按实际客户端请求计量，包括失败或结果未知的请求，不能因没有得到答案就自动退还预算。供应商内部搜索次数与客户端请求数是不同指标，不能混作同一种消耗或直接推算费用。人工等待按现有规则处理。

资源不足、数据缺失或工具不可用，应如实反馈。不能因此自行扩大授权、更换研究目标或替换数据集。

### 5.2 申请、批准和实际执行分开记录

批准绑定准确的操作、参数、上下文与身份，并在执行前持久消费。执行仍检查当前权限和目标，不能复用批准执行另一项操作。

阅读用户答案不等于批准已消费，也不代表操作已发生。结果未知时，不自动重放可能已有副作用的操作。授权到执行的完整路径必须能追溯，不能只验证一个审批函数。

### 5.3 回答继续原工作，重试才建立新尝试

任务 Agent 得到回答后继续同一 Task/Attempt/Session；Scientific 继续同一 Run/Session。任务失败后的 retry 才创建新 Attempt，科学层重新提出工作则是新 WorkRequest。

答案必须匹配原问题与作用域，不能重复消费旧答案。恢复不得重置预算、工作区基线或授权。paused 时补入材料只登记材料，不消费答案、启动执行或改变权限。

### 5.4 如实呈现部分结果和正常失败

工具回执要区分有效材料、成功但为空、不完整结果和失败原因。不完整结果仍需保留契约允许使用的有效来源；当前 DeepSeek 搜索只对已有有效来源的 `max_uses_exceeded` 返回 partial，畸形条目等仍整批失败。具体策略属于[网页工具契约](CONTRACTS.md#web)，不能写成所有供应商的通用保证。

错误处理本身也必须满足输出契约：异常未必带有非空消息，转换时补足合法错误字段，并确认失败状态确实持久保存。正常失败有结构化原因和状态转换；执行中断表示结果可能未知，应沿检查点和既有恢复规则处理。

可选 trace 或日志的写入失败不能覆盖业务成功或原始业务错误，应隔离诊断错误并给出有界告警。但权威状态保存失败不能吞掉，两者不能使用同一种“尽力而为”策略。

**当前边界**：系统以单 Run 单写入者为前提；应用层权限不是操作系统沙箱；跨文件保存不是事务；系统不能保证所有外部副作用恰好发生一次。设计和验证都应尊重这些边界。

## 6. 简洁实现：优先修好已有路径

### 6.1 抽象来自真实的同语义复用

修改优先沿已有生产路径，依次考虑删除死代码、修正权威来源、复用现有函数、补小型纯函数或明确的事实校验。只用一次的局部处理通常留在所属模块；已经属于公共运行机制的能力按既有边界放置。

有真实、语义一致的重复需求时才提取共享机制。不要为了可能的未来需求建立基类、管理器、插件框架或更多控制层；也不要把仅表面相似、责任不同的校验强行合并。

### 6.2 扩展沿已有接口，变化同步到全部消费者

| 变化 | 应检查的修改范围 |
| --- | --- |
| 替换 Agent、模型、存储或搜索后端 | 接口实现、入口装配、对应行为测试；调用方不识别具体实现类 |
| 增加普通工具 | Tool、输入 schema、所属 Agent 的显式工具与动作列表；不复制通用循环 |
| 增加有副作用的操作 | 上述范围，加授权快照、执行、失败、消费和恢复；工具登记本身不授予权限 |
| 增加公共字段或顶层角色 | 明确职责变化，同步生产者、校验、消费者、持久化、装配、版本和测试 |

接口清理保留一条生产主线，同步删除不可达分支、无消费者字段和已被取代的逻辑。当前 schema 不兼容的旧 Run/Session 明确拒绝恢复，不留下无人使用的兼容层；磁盘构建产物也不能当成第二套实现来维护。

### 6.3 防御要对应真实边界和可处理后果

外部输入、供应商响应、文件事实和恢复状态需要按契约校验。内部已经有权威保证的事实，不应层层重复猜测、宽泛捕获后返回默认值或悄悄降级。

新增保护时说明：哪里会产生坏输入、当前约定如何被破坏、接收端应该怎样反馈。若只能解释为“万一以后用到”，通常还没有建立新增机制的依据。

## 7. 修改、评审与验证的方法

### 7.1 先证明问题，再提出最小改动

一个可操作的 finding 应能沿“入口 → 数据路径 → 断点 → 实际后果”复现，并说明现有测试为何没有覆盖。个人偏好或“看起来复杂”不等于缺陷。

检查完整链条：谁产生信息、谁验证、谁保存、谁消费；成功、失败、问答、重启时是否连续。涉及模型输入时要检查实际构造出的请求，不只检查某个中间转换函数。

### 7.2 十二项修改检查

下面是前文原则的速查表，不再建立另一套规则。

| 检查项 | 评审应回答的问题 |
| --- | --- |
| 1. 职责 | 改动仍由正确的 Agent 或代码层承担吗？ |
| 2. 公共边界 | 是否出现 Agent 互调、反向依赖或读取私有状态？ |
| 3. 统一 IO | 工作是否仍通过统一请求、结果和少量控制字段表达？ |
| 4. 共享循环 | 是否复制循环，或在通用机制加入专业业务分支？ |
| 5. 判断与事实 | 有没有用关键词替代语义判断、用报告文字推断机器状态？ |
| 6. 权威来源 | 是否新增第二份独立事实或让派生目录授予权限？ |
| 7. 控制流程 | Controller、Scheduler、AgentLoop 的边界是否保持？ |
| 8. 回答与重试 | 身份、问答作用域、Attempt 和恢复是否连续且不重复消费？ |
| 9. 总约束 | 内部调用是否继承 Run 预算、期限和授权？ |
| 10. 批准与执行 | 是否绑定准确操作、持久消费，结果未知时是否避免自动重放？ |
| 11. 材料与完成 | 是否保留完整索引、原件入口、来源冻结和各层完成要求？ |
| 12. 历史与清理 | 失败、用量、原事件是否保留；旧字段、死分支与文档是否同步清理？ |

### 7.3 验证证据与结论匹配

| 验证方式 | 可以证明 | 不能单独证明 |
| --- | --- | --- |
| 确定性、契约与边界测试 | 状态、集合、长度、身份、失败和恢复符合约定 | 真实模型总会作出好选择 |
| mock E2E | 公开入口能把模块组合成完整流程 | 真实科研任务质量和检索质量 |
| 真实材料与真实 L3 | 指定配置、任务和模型轨迹的完成情况 | 通用成功率、普遍质量提升或商业搜索水平 |
| 成对质量对照 | 在控制条件下比较某项行为或交付 | 超出样本与条件范围的整体提升 |

测试承诺的实际性质，而不是照抄实现。例如测哈希身份稳定性、不同路径不碰撞、失败不破坏原件、完整目录的集合相等、持久恢复与工具回执配对。

基准来自实际来源、冻结原件或独立计算，不凭测试者记忆。差异出现时先核对来源与校验方法；保留首轮失败和更正理由，不修改被测产物或放宽断言来获得通过。检查命令见[开发与验证](../guides/DEVELOPMENT.md#local-checks)和[测试目录](../../tests/README.md)。

### 7.4 文档维护同一套当前事实

设计原则保存理由与可复用方法；架构、契约、上下文分别维护结构、接口和模型输入。重要取舍追加 ADR 并注明取代关系；阶段审查、计划与验收放 history，不能把尚未实施的方案写成当前能力。

代码行为变化时同步相应当前文档与使用示例。不要在多份文档重复维护字段表、预算数值、供应商差异或测试总数。发现文档与实现不一致，明确修正其中一方，不以“文档是权威”忽略差异。
