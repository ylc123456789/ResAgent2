# Run 预算、权限与操作检查简化方案

日期：2026-09-22。状态：方案已批准，正在实施。

基线：`refactor/unified-agent-entry`，`c0add70`，schema 12.0。实现分支：从该基线直接派生的 `refactor/run-control`，目标 schema 13.0。原分支保持未合并。

实施前复核确定：授权在创建 Run 时持久固定，内部请求缺少权限不得默认放行；工作区声明与授权共用 `WorkspaceAccess`；审批快照通过 question/answer 工件传递，执行前消费；用量存入既有 Run 原子 JSON，结果回传不再扣费。HTTP 使用支持取消的客户端落实总截止时间，不以 socket read timeout 代替。

## 1. 建议结论

采用一套以 Run 为上限的控制机制。用户决定这次 Run 可以花多少、访问哪里、执行哪些类别的操作；系统负责把这些限制传给内部模块，内部只能继承或收紧。

权限和安全共用一个执行判定入口，结果只有 `allow / ask / deny`。内部仍区分两件事：权限判断“是否在授权范围内”，安全规则判断“范围内的这次操作是否需要确认”。二者不拆成独立服务，也不混成一个可以随意覆盖的布尔值。

首版采用固定代码规则，不引入安全模型、规则 DSL 或多级审批。普通编辑、删除文件和清理目录都有明确可用的工具；限制危险命令不能把正常开发工作堵死。

三个 Agent 继续只有 `invoke(AgentRequest) -> AgentResult`。做什么仍只通过 `instruction + artifacts` 表达；预算、权限和确认字段只控制执行边界，不恢复业务模式。

## 2. 当前能力与实际缺口

| 当前事实 | 本轮如何处理 |
| --- | --- |
| Run 已统一模型调用计数和时间；`max_steps` 已在此前删除 | 延续已有设计，不重新发明步数预算 |
| `RunBudget` 混放任务数、尝试数、模型调用数、时间 | 把消费预算与流程保护分开命名和展示 |
| Scheduler 当前串行执行，子调用获得 Run 剩余额度 | 沿用共享余额，不做按 Agent 百分比分配 |
| Agent 调用结束后汇总计数，中断可能丢失未回传用量 | 在真正发出模型请求前持久登记 |
| HTTP、重试、命令等没有完整沿用同一截止时间 | 补齐截止时间传递和取消 |
| 存在权限字段，但 Run 到 Agent 的传递不完整 | 让 Run 成为唯一授权来源，消除各模块默认放行 |
| `replace_text(new_text="")` 已能删除匹配内容；没有删除文件工具 | 沿用文本编辑，新增一个 `delete_path` |
| 已有问题、回答、暂停和同一 Attempt/Session 恢复 | 复用它们承载结构化、单次操作批准 |
| `.git` 与 `__pycache__` 等目前共用保留目录集合 | 区分受保护元数据与普通可重建缓存 |

数据集发现、下载缓存、环境复用和依赖安装缓存继续沿用现有机制。镜像选择和安装预检不进入本方案，也不新增 GPU、数据集、依赖的通用配额系统。

代码依据：[契约](../../../packages/contracts/src/resagent2_contracts/models.py)、[Run 状态与计时](../../../packages/orchestrator/src/resagent2_orchestrator/models.py)、[调度与授权构造](../../../packages/orchestrator/src/resagent2_orchestrator/scheduler.py)、[路径边界](../../../packages/components/src/resagent2_components/workspace.py)、[文本修改](../../../packages/capabilities/src/resagent2_capabilities/workspace/replace_text.py)。

## 3. Run 控制数据

| 数据 | 谁决定 | 用途 |
| --- | --- | --- |
| `RunBudget`：`max_llm_calls`、`timeout_seconds` | 用户/可信调用方 | 本次 Run 可以消耗多少 |
| 工作区授权、`execute_commands`、`prepare_environment` | 用户/可信调用方 | 本次 Run 可以访问和操作什么 |
| `confirm_commands`，默认关闭 | 用户/可信调用方 | 是否额外要求每次 Agent 发起的外部命令先确认 |
| `ExecutionLimits`：`max_tasks`、`max_attempts_per_task` | 系统配置，创建 Run 时固定并保存 | 防止无限拆任务、无限重试；保留现有默认值 |
| `RunUsage`、等待用户的时间、待确认操作 | 系统维护 | 已经花了多少、目前停在哪里 |

这些是同一机制里的不同数据，不再套一个多层资源管理框架。`ExecutionLimits` 仍可作为高级配置，但不与模型次数、时间混称为同一种预算；触发时报告“任务数上限”或“尝试数上限”。已有 CLI 的相关高级选项可保留。

`TaskBudget` 保留为本次调用的上限快照，不开第二个钱包。Run 状态与执行时检查才是最终依据。各模块不得自行增加额度，模型提出的工作请求也不得设置权限或刷新余额。

## 4. 预算：一个余额，一只时钟

### 4.1 模型请求次数

保留字段名 `max_llm_calls`，用户说明写清楚“模型请求次数”。每次进入模型 HTTP 发送阶段计一次，包含失败重试、格式纠正、上下文压缩，以及 Scientific、Compiler、Coding、Experiment 的调用。

工具执行次数、Agent 回合数、上下文容量都不等于模型请求预算。Token 用量和可获得的费用继续作为观测信息；本轮不增加金额硬上限。

例如 Run 上限 200 次，Scientific 使用 10 次、Compiler 使用 5 次，下一个 Agent 可使用的 Run 余额就是 185 次。某个 Agent 结束、换任务或恢复进程，都不重新获得 200 次。

### 4.2 先登记，再发送

扩展现有 Run 状态和原子 JSON 保存能力，在 Run 内保存小型请求用量记录；不新增数据库、独立账本服务或事件溯源系统。

1. 参数、权限和时间检查通过后，为这次真实请求生成身份，使用已有 `call_id + retry_index` 关联 trace。
2. 通过调用方注入的受限用量接口检查余额，并将此次占用原子保存；保存失败就不发送。
3. 发出请求，结束后补记成功、失败等结果。不同 HTTP 重试分别计数。
4. 崩溃时已经占用、但没有结果的请求保留为“结果未知”，恢复时不退款、不自动重放。

登记后、真正发送前崩溃，可能保守多占一次；这是避免恢复后超额的明确取舍。该计数是预算占用，不冒充供应商精确计费。报告分别展示占用次数、已知结果和未知结果。

`llm_calls_used` 从这份状态计算；`AgentResult` 的用量只用于诊断与对账，不再二次扣除。Controller 不通过读取 Agent 私有 Session 补账。受限用量接口由组合根注入 Runtime/Compiler，不把服务对象放进序列化的 `AgentRequest`。

首版保持同一 Run 单一执行者和串行调度，不设计并行配额预约。独立调用模块也由可信调用方提供同样的预算上下文，不能形成另一种业务入口。跨进程恢复读持久用量；并发驱动同一个 Run 不在本轮支持范围内。

### 4.3 时间

沿用当前定义：从 Run 创建开始，扣除明确等待用户回答的时间；安装、下载、模型等待、命令运行和普通进程停机时间都计入。

- 每次开始或恢复执行，按 Run 剩余时间生成本次有效截止时间；恢复暂停不重置总时长。
- 内部传递同一个截止时间。HTTP、退避等待、安装、验证、训练的可用时长都是“操作自身超时与当前 Run 剩余时间的较小值”。
- 每次重试、每条批量命令开始前重新计算余量，不从最初快照重新获得完整超时。
- 截止时间到达后停止新工作，并取消在途请求、终止受控命令及其子进程。记录取消或结果未知，不能只在返回后发现已超时。
- 网络库的 connect/read timeout 不一定等于总耗时上限，实现时必须验证总截止时间和取消路径，不能只改一个 timeout 参数就宣称完成。

本地取消请求不保证供应商已经停止计算或计费；没有收到确定结果时，保留已经登记的预算占用并注明未知。

预算用尽后通过已有确定性结果路径保存现状和停止原因，不额外调用模型生成结尾。资源已经耗尽与操作被拒绝是不同结果，不用 `deny` 混报预算错误。

## 5. 权限：从 Run 派生，不能逐层放大

### 5.1 文件范围只保留一种表达

工作区来源仍由 `WorkspaceSpec` 声明，物理路径由可信的 workspace resolver 解析。工作区权限统一使用相对路径前缀：

```yaml
read_paths: ["."]
write_paths: ["src", "tests", "results"]
denied_paths: ["private", ".env.local"]
```

含义：允许读取工作区，允许创建、修改和删除 `src/`、`tests/`、`results/` 内的内容，但 `private/` 和 `.env.local` 不可访问。允许列表中的 `[]` 表示没有权限，`["."]` 表示整个工作区；`denied_paths=[]` 表示没有额外排除项。不用通配符，也不用空允许列表表示无限制。写范围必须包含于读范围，排除项对读写都优先生效。

这个示例支持定点编辑和分析；没有隔离后端的首版不能在此授权下执行通用测试或训练。需要运行任意脚本时，应使用完整可读写、无用户排除路径的可信工作区；不能靠一次批准绕过局部范围要求，详见第 5.3 节。

让 `WorkspaceSpec` 和解析后的 `WorkspaceGrant` 复用这一小型路径范围结构：前者是声明，后者是其确定性投影。把当前 `mode + allowed_paths + denied_paths + 组件私有 write_paths` 收敛为 `read_paths + write_paths + denied_paths`；只读是 `write_paths=[]` 的结果，不再并存可冲突的权限字段。沿用现有排除能力，不要求为了排除一个敏感文件而枚举整个项目。

Agent 请求中的工作区必须是 Run 已登记的工作区或由可信解析器在本次 Run 管理目录内创建的工作区。模型可请求工作区 ID，不能自填任意物理根路径取得授权。声明、解析、Agent 请求之间必须校验一致性。

输出目录由系统在 Run 目录内分配，与源代码范围分开；因此只读分析仍能保存报告。冻结工件、数据集缓存和环境缓存继续由已有专用组件按其职责访问，不把缓存根目录授予 Agent 任意文件写入权限。环境管理权限只授权受控环境操作，不等于可以任意删改共享环境。

### 5.2 操作权限

Run 明确保存 `execute_commands` 和 `prepare_environment`，创建入口可以解析出明确默认值，但 Agent 边界缺少授权不能自动变成 `True`。`prepare_environment` 包括已有受控环境管理；`execute_commands` 控制 Agent 发起的验证、审计和实验等进程操作，两者沿用现有不同职责。

`request_work` 是 Scientific 的角色能力，仍由代码限定；它不表示 Scientific 可以扩大 Run 的权限。Coding/Experiment 也不会因为路径可写就自动获得对方所有工具。

派生规则为：**实际权限 = Run 授权与本模块可用工具能力的交集；任务有明确收窄要求时，再取交集。** 当前不新增由模型填写的一套任务 ACL，也不设计自动权限分配器。默认继承已经足够。

路径继承中，读写允许范围只能取交集，排除范围只能保留或增加；子调用不能清空上层的 `denied_paths` 恢复访问。

自然语言“随便修改”“已经批准”以及历史回答内容都不能改变结构化权限。首版 Run 开始后不提供自动扩权；超范围必须停止该操作，交由调用方另行调整授权或新建 Run。

### 5.3 必须明确的执行边界

路径工具可以在每次访问时强制检查授权、规范化路径和链接逃逸。但现有 `ProcessRunner` 使用宿主账户运行程序，即使采用 `shell=False`，`python train.py` 仍可能访问工作区外的文件。

因此本轮提供的是“结构化工具的范围检查，加上可信代码执行的误操作防护”，不是对恶意脚本的操作系统沙箱。固定命令规则无法证明任意 Python 代码安全；审批也不能把这一点变成安全保证。

没有隔离后端时，源工作区只读、用户限定局部读写范围或配置排除路径的请求不开放任意脚本执行，即使 `execute_commands=true` 且用户批准也不能绕过。完整可读写、无用户排除路径的工作区可执行可信脚本；即便如此，也不能承诺宿主其他路径或工作区元数据在操作系统层不可访问。内建元数据保护仍是工具规则，不冒充脚本隔离。

若后续要求“无论脚本做什么都不可能越界”，必须接入真实 OS/容器隔离。可以复用同一 Run 授权投影到隔离后端，不应继续堆命令黑名单。本轮不顺带开发这一后端。

## 6. 一个操作检查入口

沿用现有工具执行链，将 `PermissionDecision` 从布尔结果改为 `allow / ask / deny + 原因`，共用确定性策略函数。顺序为：

```text
预算/截止时间仍有效
  -> 工具能力、Run 操作权限和路径检查
  -> 固定操作规则
  -> allow: 执行 / ask: 保存待确认操作并暂停 / deny: 返回拒绝及原因
```

共享函数负责决策，实际文件/进程组件仍在操作发生前检查边界，避免绕过入口。不要在三个 Agent 内复制三套规则。现有 Experiment 的 setup/experiment 命令分类是工作流分类，不当作安全判断。

| 操作 | 默认判定 | 说明 |
| --- | --- | --- |
| 读取已授权文件 | allow | 仍检查真实解析路径 |
| 新建、修改、删除文件中的一段内容 | allow | 在写范围内即可，不因替换为空就询问 |
| 删除写范围内单个文件或空目录 | allow | 通过结构化 `delete_path` |
| 递归删除写范围内非空目录 | ask | 展示准确目录、文件数和待删除范围 |
| 删除工作区根、访问越界目标、改动受保护状态目录 | deny | 用户对某次操作回答“同意”也不能越过 Run 边界 |
| 常规受支持的测试、验证、直接运行工作区脚本 | allow | 仍须有执行权限、符合模块工具约束和上述执行边界 |
| 任意内联解释器代码或规则未覆盖的可执行命令 | ask | 展示原始参数；不尝试证明脚本语义安全 |
| 裸 `rm/rmdir`、明确的破坏性系统命令、提权、shell 包装 | deny | 删除用结构化工具；继承无 shell 拼接的既有限制 |
| `confirm_commands=true` 时的 Agent 外部命令 | ask | 在权限允许的前提下，额外逐条确认 |

命令规则依据规范化 executable/argv 和少量明确子命令，不能用“字符串包含 rm”这类匹配。固定拒绝包括明显的磁盘格式化、关机、提权和破坏性 Git 操作；不引入任意脚本分析器。既有受控依赖安装仍走环境工具，不能借普通命令绕过环境权限。

`confirm_commands` 不会要求对框架内部固定的每个 git 探针、环境管理子进程分别答题；Agent 发起的顶层环境操作按权限和适用确认规则检查。被拒绝时给出具体原因和可用工具，允许 Agent 在剩余额度内改用合法操作。

### 6.1 正常删除的实现

新增 `delete_path(path, recursive=False)`，只接受一个准确的工作区相对路径。首版接入已有源码编辑能力的 Coding，不顺带赋予 Experiment/Scientific 源码修改能力。删除后沿用 `edit_revision`、diff 和验证失效机制。

- 删除文本仍使用已有 `replace_text`；不额外引入“删除内容”工具。
- 文件和空目录直接删除；非空目录只有显式 `recursive=True` 才生成确认。
- 非空目录确认保存待删除条目的相对路径、类型及版本信息摘要。执行前重验授权及目标集合；内容变化则旧批准失效，不直接对当时目录无条件 `rmtree`。
- 每个实际删除对象都必须在写范围内。删除链接时检查链接自身的词法路径可写，解析父目录检查根内边界和链接逃逸，只 unlink 链接本身，不读取或遍历目标。不要求整个父目录都可写；不能复用跟随最终目标的写文件解析来做删除。
- 新建文件也按最终路径授权：例如已授权 `results/`，该目录尚不存在时可以创建，不能误要求最近存在的祖先目录也整体可写。父目录解析和路径竞争仍须复查。
- `.git`、Run 状态、`.resagent2` 等元数据仍受保护；`__pycache__`、`.pytest_cache` 等只是展示时可忽略的可重建目录，允许按同一清理规则删除。
- 不承诺目录删除原子回滚。中断或条目变化时保留已完成和未完成记录，不自动重新执行整次删除。

文件写权限本来就允许清空文件，连续的合法单文件删除也可能造成大量损失。因此“目录删除确认”用于减少误操作，不宣称它能防止恶意 Agent 的所有破坏。

## 7. 确认复用现有问答，只批准这一次动作

复用 `QuestionDraft / PendingQuestion / RecordedAnswer`、不可变 answer 工件和当前暂停恢复流程。不新增审批服务、审批 Agent 或新的调用模式。

待确认操作保存结构化身份：`action_id`、工具名、规范化参数、实际工作目录/目标/环境、所属 Run/Task/Attempt/Session；目录删除另带目标摘要。问题正文用于让人理解，匹配依据不再依赖问题文案。

执行方 Session 保存待确认动作及其消费状态，question/answer 工件携带不可变公开快照；Controller 沿用公开结果和工件转交确认，不读取私有 Session。`AgentRequest` 不新增第二个业务指令字段。

用户批准后，执行前重新检查当前预算、权限和目标。批准只在这次派发前持久标记为已消费，同样字符串的下一次命令也不复用旧批准。批准记录本身不扩大权限。

如果消费批准后进程崩溃、没有执行回执，沿用现有“结果未知、不自动重放”的恢复原则。过期问题、别的命令、别的任务的回答全部拒绝，并保持 Run/Session 状态不变。

删除 `experiment_confirmed` 的全局放行含义，收敛 `confirm_before_experiment` 到 Run 的 `confirm_commands`。普通业务提问仍是普通问题，用户只需按现有入口回答，不接触内部动作 ID。

命令确认绑定这次命令及执行上下文，不承诺冻结任意脚本间接读取的全部文件。需要更强隔离或可复现源码冻结时，应走专门的执行后端或现有证据冻结流程。

## 8. 修改顺序与验收

方案确认后再开始产品实现；可以从当前未合并分支派生子分支，无需先合并。建议四段提交：

1. **控制契约和继承。** 精简预算字段，固定执行限制，统一路径范围，补齐 Run -> Controller/Scheduler -> Agent 的权限传递；取消内部默认扩权。
2. **预算执行。** 在 Run 原子存储内增加请求登记，移除结果回传后二次扣费，补齐 Runtime/Compiler/HTTP/重试/命令的截止时间和中断恢复。
3. **操作与确认。** 复用决策类型和问答机制，新增 `delete_path`，拆分元数据保护与缓存忽略规则，加入少量 argv 规则和单次批准。
4. **集成和文档。** 更新 CLI、当前架构/契约说明及测试交接；完成确定性回归，再做小规模真实模型验收。

本次契约有破坏性变化，实施时统一提升 schema，不同时保留新旧两套权限解释器。旧 Run 和证据保留可查，首版不提供跨 schema 继续执行的迁移。

确定性验收必须覆盖：

- 三个 Agent、Compiler、格式修复、压缩和 HTTP 重试共享一次数余额；耗尽不再请求模型。
- 发送前持久化失败不发送；登记后崩溃不退款；跨进程恢复不重置；结果返回不重复扣费；未知请求与实际计费如实区分。
- 批量命令及重试共享截止时间；用户暂停扣除；安装和下载计时；取消后没有遗留受控子进程。
- Run 不授权的工具/路径不能由 Task、instruction、恢复回答或默认值重新打开；只读分析仍可保存输出工件。
- 排除路径优先于读写授权，子调用不能清除；受限工作区即使有执行开关及批准也不能启动任意脚本。
- 删除几行、单文件、空目录正常可用；非空目录确认；缓存可清理；根目录、元数据、路径逃逸和链接目标受保护。
- 精确授权一个链接时能删除链接自身而不触达目标；授权目录尚不存在时能在其内创建文件，不额外要求父目录整体可写。
- 批准一次只执行一次；目标变化重新确认；拒绝旧答案时保存完整前后状态证据；崩溃不自动重放。
- 固定命令规则覆盖允许、确认、拒绝及误匹配边界；明确测试不把任意 Python 执行当作沙箱。

现有统一 IO 回归和真实流程继续作为基线。历史测试为 1071 passed / 1 skipped，新增测试后以实际计数为准。真实模型只补“修复并删除旧文件”“目录清理确认”“命令确认恢复”“小预算终止”等受影响流程；不为确认/计费逻辑单独重装依赖或重复 GPU 训练。若安装、训练命令路径实际变动，再针对性复跑既有场景。

## 9. 借鉴依据与取舍

- [Saltzer 与 Schroeder：保护机制设计原则](https://web.mit.edu/Saltzer/www/publications/protection/Basic.html)：最小机制、最小权限和每次访问检查。对应单一判定入口、组件边界检查及禁止内部扩权。
- [OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)：默认拒绝、每次请求检查授权。用于技术授权边界，不把正常编辑都变成人工确认。
- [OpenHands 固定版本确认策略](https://github.com/OpenHands/software-agent-sdk/blob/97dbce5c37865dd7a3020d2b9662f4a76d11fa71/openhands-sdk/openhands/sdk/security/confirmation_policy.py)：可用确定性策略表达何时确认。只借鉴这一点，不照搬整套风险系统；本项目额外明确子任务不能扩大 Run 权限。
- [Pydantic AI 多 Agent 共享用量](https://github.com/pydantic/pydantic-ai/blob/255a109e8b4d2869298ac3f6d968c581e90cdd15/docs/multi-agent-applications.md)：共享 usage 比各自记账更清楚；共享对象不等于自动继承 limits，也不解决崩溃持久化，因此这里由 Run 统一限制和登记。
- [gRPC 截止时间](https://grpc.io/docs/guides/deadlines/)：下游继承剩余时间，取消需要各层配合。用于 HTTP、工具和命令共享截止时间，不引入 gRPC 依赖。
- [Google SRE：过载处理](https://sre.google/sre-book/handling-overload/)：重试不能无限放大工作量。这里让重试同时受 Run 次数和时间限制，避免再加第三套重试消费预算。
- [AI Agents That Matter](https://arxiv.org/html/2407.01502v1)：评价 Agent 应同时关注结果与成本；保留用量观测，但不把步数或请求次数包装成精确货币成本。

本方案不依赖“Codex 一定由某个专用模型判断安全”的内部实现假设。当前需要的是可理解、可测试、不会妨碍普通开发工作的固定规则，以及明确承认规则无法替代 OS 隔离的边界。
