# 模型实际会看到什么：上下文说明

三个 Agent 使用同一套上下文。Scientific 负责研究判断，Coding 和 Experiment 负责专业执行；它们的差别主要是身份提示、工具和领域完成检查，不是另一套记忆架构。本文从模型输入讲起，再说明工具、工件、压缩和恢复。职责见 [ARCHITECTURE](ARCHITECTURE.md)，字段见 [CONTRACTS](CONTRACTS.md)，取舍见 [DESIGN_PRINCIPLES](DESIGN_PRINCIPLES.md)。当前 schema 为 **29.0**。

<a id="basics"></a>

## 1. 四部分各负责什么

| 部分 | 内容 | 是否允许从模型输入中压缩或省略 |
| --- | --- | --- |
| 固定契约 | Agent 身份、系统规则、实际启用工具的说明和 schema | 不允许；同一 Session 保持稳定 |
| 任务需求 | 初始上级指令、必要控制事实、有序上级补充与向上业务问答 | 不允许；业务回答追加保留 |
| 原生 assistant/tool 历史 | 工具调用、直接回执、运行时通知、下级问题与自身答复、当前共享预算、必要历史摘要 | 只有这一部分可以压缩较早的完整回合 |
| 完整工件索引 | 当前 Agent 已授权的全部登记材料，以及 WorkRequest → Task → 实际产物导航 | 不允许选择或截断；不包含正文工作集 |

“完整”指当前 Agent 的授权范围，不是整个 Run 的全部内部记录。索引说明材料在哪里；工具读取提供材料内容；读取过不证明内容支持结论。

每轮重建第二、第四部分，使用最新已保存的事实。重建不会重新执行搜索、读取文件或命令。第三部分连续保存近期原生回合，过长时只改变较早回合的模型投影；系统的原始事件和回合仍保留。第一、第二、第四部分以及必要近期回合装不下时明确失败，不能偷偷删除索引条目或任务要求。

## 2. 实际发送给模型的形状

```text
messages:
  system     固定原生协议规则 + Agent 身份和规则
  user       完整任务需求、初始控制事实和累计业务问答
  assistant  存在时的较早工具历史摘要（属于第三部分）
  assistant  原生模型内容、reasoning、tool_calls
  tool       对应 call_id 的唯一回执
  ...        其余近期完整回合及有来源的运行时通知
  user       尚未回答的下级问题（第三部分的当前待处理事实）
  user       当前 Run 共享总预算（第三部分，发送前从用量账本刷新）
  user       完整工件索引
tools:       本 Session 实际启用的固定工具 schema
```

四部分是职责划分，不强制对应四条 API 消息。Agent 身份是真正的 system 内容；工具 schema 只通过原生 tools 参数提供，不再复制一段工具契约文本。工具注册表同时负责向模型展示、参数校验和派发。

Session 保存协议身份及固定契约指纹。指纹涵盖实际 system 内容（身份 prompt 与通用原生协议规则）和实际工具 schema；恢复时更换模型、endpoint、身份、协议规则或工具集合会明确拒绝。API key 和动态预算不进入指纹。供应商 reasoning 与对应原生回合一起保存，不作为科学证据。

源码：[消息投影](../../packages/runtime/src/resagent2_runtime/tool_calling.py)、[循环](../../packages/runtime/src/resagent2_runtime/loop.py)、[Composer](../../packages/runtime/src/resagent2_runtime/context.py)。

## 3. 任务需求和问答

第二部分来自 `AgentRequest.instruction`、`task_context`、`upstream_inputs` 和同作用域业务回答；模型投影只保留一份按时间排列的 `business_dialogue`，不再并列复制输入/答案数组。它只接收上级要求：主 Scientific 的上级是真实用户，执行 Agent 的上级由 `upstream_session_id` 明确指定。`parent_session_id` 仍表示恢复自身的旧 Session，不用于判断上下级。必要的工作区、权限、数据集和验收事实保留；环境和版本要求沿自然指令及共同限制原文传递，不再投影系统绑定或认证状态；自然指令和共同限制逐字符传递，不交给 Compiler 改述。

`business_dialogue` 按原事件时间与身份排列输入和答案。原记录与来源完整保留；后来的同作用域明确修改覆盖被修改的选择，其余要求继续有效。转发旧用户记录保留原时间和身份，不把转发时间当成用户重新发出指令。父 Agent 的解释标为 parent，不能冒充用户原话或覆盖明确用户要求。代码保证记录和顺序，通用提示词负责语义；含义或优先级不清楚时向直接上级提问。

所有 Agent 使用同一个业务 `ask_user`。有直接父 Agent 时，问题绑定原 Task、Attempt、Session 和问题 ID，暂停提问方；Controller 暂时唤醒父会话处理。根 Scientific 才把问题交真实用户。父方向用户升级提问时用 `related_question_id` 绑定原子问题；旧委派结束后，相关升级问题一并失效。父方通过 `reply_to_task` 回答准确问题或主动澄清自己的有效子任务，必要时先向自己的上级 ask_user。父方不能代替权限系统批准命令。`reply_to_task.resume_work=false` 可先逐个任务传递澄清而不恢复子执行；最后一次答复使用 `true`（默认值）再继续工作。未答业务问题和待批准操作仍保持等待。转发普通输入引用 `user_input_event_id`，转发真实用户答案引用 `user_answer_question_id`；代码复制原文、值和原事件时间，保留原问题 ID，模型不能改写后标成用户原话。

方向决定上下文位置：子 Agent 的完整问题、上级答复及来源进入子方第二部分；父方收到下级问题及自身答复属于第三部分，不进入父方目标/需求。下级问题保存成有来源的运行时通知，不伪造父方工具调用。尚未回答的问题从同一 Run 记录再投影到当前第三部分，历史压缩不能使它失联；回答后历史通知可以随第三部分压缩。不生成 question/answer 工件，不新增问题索引，第四部分不变。

问答在原 Task、Attempt、Session 继续，失败 retry 才建立下一 Attempt。选项只是提示，业务字段可自由输入；权限 comment 仍是另一用途。用户普通补充不是待答问题的答案。普通补充立即保存；当前模型请求及已采纳工具批次正常完成后，在下一次模型判断前由 Scientific 处理，不能等整项 WorkRequest 结束。暂停的 Run 收到补充也不会自行恢复。

Scientific 的权限展示区分两个作用域：current_agent_permissions 只描述本角色可用能力，run_execution_permissions 描述 Run 对执行子任务的授权。两者由固定代码从当前请求和权威 Run 投影为第三部分 runtime_authority，不作为第二部分目标/限制，也不产生工件或持久审批记录。Scientific 自己不能执行命令，不代表子任务也被禁止；它不能将本角色限制改写为整个 Run 的权限或让模型通过任务文字传递授权。子任务实际权限仍由 Scheduler 继承或收紧。该运行时事实每轮重建、参与完整容量检查；刷新预算及 HTTP 重试不会移除它。

操作审核由 Run 创建时的 approval_mode 选择，manual 默认逐次交人工，auto_review 用无状态模型明确允许或转人工。审核模型不复用执行 Agent 的 Session 或工具历史，而由固定代码提供完整当前任务与上级业务对话、根用户原始要求和业务修订、准确操作快照；历史人工操作决定及说明另成有来源的输入区，不混入目标要求。授权意图与实际效果证据分别判断：用户要求执行、描述预期输出或要求跳过检查，都不证明未提供代码的实际行为；cwd 和工作区授权也不是沙箱。脚本效果不能从所给资料确认时应转人工，不自动读取额外材料，也不以先执行后核对替代事前审核。输入容量不足也不裁剪用户要求后继续放行。

审核开始和结果保存在发起 Session 的 permission_review 事件中，唯一工具回执携带 auto_review 来源、状态、原因及事件序号。它们属于第三部分，不冒充用户回答，不进入第二部分或第四部分，也不新增审批工件；第三部分原始事件仍保留。自动审核和人工批准都受同一硬授权及准确快照约束，审核的模型调用消耗整个 Run 总预算。

操作批准也使用暂停、回答入口，但有不同用途。它绑定准确工具、参数、目录、进程启动配置和作用域，权限策略消费它；决定及可选 comment 不进入第二部分，也不生成工件。comment 按原文保存在答案中，仅随匹配动作的原工具回执以顶层 `user_comment` 交给模型，原业务 value 不变：拒绝同时说明 `execution_status=not_executed`，批准说明则随实际执行成功或失败返回。说明本身不授予权限或改变任务，模型结合它与已有需求决定后续行动。

原操作的 native call 保持待回执，恢复后重新检查权限与快照，执行或拒绝后为原调用保存唯一最终回执，不追加另一条说明回执。快照仍匹配的普通批准无需模型重新发一次命令。批准在副作用前持久消费；批准后派发期间期限中断，原回执仍保留说明，以 `execution_status=unknown` 表示可能存在部分执行，不能写成拒绝时的 not_executed，也不自动重放。已回答旧审批后若快照变化而需要重新批准，原调用以 not_executed 结算，保留原说明并告知模型旧决定已失效；模型按需提出新的 native call，再发起新审批，不在同一调用下生成第二个问题 ID，也不套用旧说明。批准消费后仍在进程启动前复验 cwd、Shell flags 及过滤后启动环境指纹（实际环境和指纹输入均剔除 Bash 重建的 SHLVL/_ 和 SSH 连接信息 SSH_CLIENT/SSH_CONNECTION，PATH 等仍参与比较）；不一致时原调用明确 not_executed，不沿新配置执行。CLI 的 `answer --comment` 和 shell 的 `/answer` 交互入口沿同一回答链路提交，完整使用方式见 [CLI README](../../apps/cli/README.md)。

## 4. 完整目录怎样组织

`artifact_index` 每轮由授权输入、Session 已接收工具产物 ID 和官方登记 Ref 重建。Run 登记表是工件事实的权威来源；Session 保存已接收的身份，不保存第二份可以独立漂移的元数据目录。缺失已接收 Ref 明确报错，不静默漏项。

```text
文献材料
  论文元信息、原 PDF、提取全文：各自 ID、说明和直接来源关系
网页材料
  已获取页面：ID、说明、类型
工作产物
  WorkRequest ID、原目标、终态
    Task ID、任务需求、状态、错误、各次 Attempt 事实
      原始报告工件 + 实际交付物条目
其他材料
  其余合法授权工件
```

这些标题是同一份目录的展示结构，不生成分类工件、索引工件或第二套组 ID。所有实际条目直接展开，不必先读取 index 文件才能取得材料 ID。

每条包含 ID、kind、media_type、说明、可选 output_name、真实生产者与 Task/Attempt/Session、直接来源关系。不复制正文、物理 URI、hash 或权限。完整目录不授权新材料。类型内保持首次接入顺序，未知合法类型仍列出。

每个工件身份只占一个条目。复用已有材料不复制或改挂到新的生产任务；新的工作通过已有 ID 表达引用关系。实际输出按真实生产 Task 放置，各次失败 Attempt 的报告仍保留。尚未执行的依赖阻塞任务只有真实导航状态，不伪造 Agent 报告；编译失败且没有 Task 时显示真实错误与“未创建任务”。

WorkRequest 没有总体报告；每个真实终态 Attempt 的报告和实际产物直接列在 Task 下。报告按原字符冻结，不再选摘、汇总或自动折行。预执行失败报告明确标为运行时来源、Agent 未启动，不能冒充专业 Agent 的工作。

源码：[共同目录投影](../../packages/components/src/resagent2_components/materials.py)、[无状态结果整理](../../packages/orchestrator/src/resagent2_orchestrator/interpreter.py)。

## 5. 工具结果如何进入上下文

| 调用 | 第三部分 | 第四部分 |
| --- | --- | --- |
| 文献/网页搜索 | 本次去重后的候选、来源、状态及完整返回信息 | 不变，不产生工件 |
| 文献/网页 fetch | 结果说明、实际工件 ID、失败或部分成功事实 | 并入真正已登记的材料 |
| read_file / read_artifact | 所选正文与实际范围、续读信息 | 不变，不产生新工件 |
| request_work | 立即返回 accepted 和 work_request_id 后暂停 | 工作结束后展开对应 Task 报告和实际产物 |
| 业务 ask_user | 已接收的问题 ID | 不变；回答加入第二部分 |
| 操作批准 | 原调用等待，执行/拒绝后保存唯一回执，包含可选用户说明 | 不变 |

搜索只提供临时线索。旧工具历史压缩后，模型可能看不到这些搜索内容；模型需要长期保留的材料应显式 fetch。工具说明明确这个边界。搜索成功、部分、空结果或失败都不登记搜索工件。

`fetch_literature(source)` 接收明确 `arxiv:`、`doi:`、`openalex:` 或授权 `artifact:` 论文来源，按精确身份查元信息、获取 PDF、提取页码标注全文；不按模糊标题猜论文。元信息成功但下载失败、PDF 成功但提取失败时，实际登记材料仍进入目录，回执说明缺口。网页 `web_fetch` 冻结 Markdown 正文并保留来源；同源同解析器同正文快照可在授权范围复用，正文变化保留新工件。本次获取时间不写入正文破坏快照复用。

去重在三处有不同含义：搜索内部去掉本次重复候选；获取边界按准确来源与内容快照判断能否复用；目录的 artifact_id 唯一是身份约束，不负责再猜资源是否相同。复用必须校验原冻结内容，不能跨 Run 或凭猜到的 ID 扩权。

读取工具共用“选行 → 字符窗口 → 单次返回上限”。行号从 1 开始，端点包含；字符从 0 开始，末端不包含，相对于所选行段。回执保留 `total_lines`、`selected_chars`、实际续读位置 `next_start_char` 和 `truncated`。连续读取保持行范围不变，使用 next_start_char；truncated=False 只说明请求窗口未被上限裁剪，不证明整份文件读完。严格 UTF-8/NUL 检查和原换行保留不变。

正文只出现在读取回执，不再投影为第四部分工作集。历史压缩可能移除精确正文；原件和完整目录仍在，需要时重新按范围读取。PDF/checkpoint 等二进制工件也完整列出，但 read_artifact 不自动解析它们；PDF 正文通过关联全文工件读取。

## 6. 专业差异保持在职责内

Scientific 的工具用于获取材料、提问、委托和形成意见；它不直接编辑工作区或训练。Coding 用同一套工具完成分析、修改和验证；Experiment 分析已有结果或执行测量。它们没有显式工作模式。

环境检查、安装、验证和实验统一由 run_shell 执行；实际命令诊断、读取和完成拒绝由对应工具回执提供。环境选择与维护由模型依据任务要求判断，没有绑定、认证或验证代次状态。代码保存真实执行记录和文件变化，校验实际交付；模型解释检查充分性与局限。它们不成为另一个第四部分状态工作集。完成拒绝先得到判断，再保存本次 finish 的唯一 accepted/rejected 回执；不会先写成功再修改旧回执。

Scientific 的 `request_work` 明确给出 Task 列表，每个 Task 仍是自然 `instruction` 加依赖、输入、未来输出绑定、交付名和工作区等控制字段。Compiler 是无状态 LLM 路由，只能通过唯一原生 `route_tasks` 工具为每个现有任务匹配注册 Agent；不能改写、增删、合并或拆分任务。固定代码校验任务图并复制原指令、共享目标和限制，保持真实来源。Interpreter 仍只组织实际状态和 Ref，不拼总体报告。无状态原生输出（Compiler、权限 reviewer）只使用调用方的 system prompt 和唯一输出 schema，不注入 AgentLoop 的行动、finish、ask_user 或工件目录协议；仍共用完整输入计量、预算、重试、取消和 trace。

普通补充和上级业务答复沿第二部分进入下一模型判断；父方收到的下级消息、答复动作和委派结束通知都属于第三部分。`reply_to_task` 的目标校验和原文转发由固定代码完成，LLM 判断澄清内容与受影响任务。提示词保持领域通用，不加入某个数据集或单次实验的例外规则。

## 7. 只压缩原生工具历史

压缩以完整 assistant/tool 回合为边界。不能留下孤立 tool 消息，也不能删除一个批次中的半组调用。较早回合形成摘要和 history_start 检查点，近期回合原样续传；原始 tool_turns、事件、reasoning 和冻结材料不删除。

摘要属于第三部分，不提升为用户需求、工件或系统规则；它是有损交接，不保证保留每个精确数字、源码或搜索线索。第二、第四部分从权威记录完整重建，不从摘要猜回。读取重要原件是取得精确内容的途径。

容量按有效模型输入上限、Agent 配置、tools、完整消息、摘要和历史共同计量。字符估算不是供应商 tokenizer。软水位为后续回执留空间；至多一次有界压缩仍超限时明确返回容量错误，保留现场。完整目录不能截断，第一、第二、第四部分没有正文配额、优先级筛选或压缩路径。

摘要请求与其他模型请求共享 Run 账本、调用上限和期限；发送前保存占用，失败/未知不退款。等待用户暂停不重置预算。

每次实际模型请求发送前，第三部分从同一 Run 用量账本刷新总调用上限、已用、剩余调用和剩余执行时间，明确这是 Scientific、Compiler、各子 Agent、后续委派和最终交付共享的总预算（也包含权限 reviewer），不是当前 Agent 或 Task 的专属额度。数值对应本次请求占用前；本次发送也消耗一次，HTTP 重试前再次刷新。内部 AgentRequest.budget 继续用于收紧执行限制，不再作为第二部分的静态额度展示。独立调用没有绑定 Run 时明确标为最外层 invocation 额度。预算投影不写入工具历史，不形成第二套账本，也不改变分配、保留额度或完成策略。

## 8. 显式打断与恢复

运行中的普通文本和显式打断是不同操作。Esc、Ctrl-C 或 `/interrupt` 关闭当前推进：模型请求取消本地等待、迟到未采纳回复失效；运行中受管工具停止进程组和子进程，未开始工具不派发。完成的真实结果和原回执保留。只有确认执行已停止后才显示 paused；无法确认时明确失败并保留 PID 等诊断，不宣称停止成功。模型供应商可能继续计算，已发出的调用不退款。

尚未返回的普通工具取得唯一 interrupted 回执；已经返回 accepted＋ID 的 ask_user/request_work 不再追加第二个 tool 回执，而是保存引用原 ID 的第三部分运行时通知。取消期间完成的原子文件写入或冻结登记先结算，不能留下半条正式索引。文件、日志、现有修改和 checkpoint 默认保留；半成品不会自动登记为成功交付，不自动 Git 回滚。

活动 WorkRequest 是打断的特殊处理：确认其当前执行结束后，将旧委派和未完成 Task/Attempt 设为 cancelled，取消其待答与批准关系，子 Session 保留审计但不复活。已完成 Task、冻结工件与实际文件保留。继续恢复 Scientific 原 Session，由它按需创建新的 WorkRequest，可明确复用原材料和逻辑工作区。普通输入/业务问答则继续原子会话。

Coding/Experiment 用同一执行记录生成逻辑处理正常完成、失败、中断和问答/让出暂停：从本 Agent 的原始工具回执提取实际命令结果，作为既有 `execution_record` 随公开 AgentResult.artifacts 交接。未执行或被拒绝的命令不生成执行事实；中断记录保留真实停止确认、退出码（若已知）、耗时和日志位置，不补造成功或推断半成品可用。若脚本已完成、后续 Git 诊断才被打断，同一唯一回执以 completed_command 保留脚本结果，并保留诊断的真实 stop_confirmed；执行工件分别记录两项事实，不把诊断未知等同于脚本未执行。同一 Task/Attempt 的相同来源、相同冻结内容快照经完整性复验后复用原工件；新增真实执行结果则保留新快照。Task 报告关联这些工件，父方第三部分的中断通知提供实际工件 ID；第四部分仍在原 WorkRequest → Task 下直接列出报告和执行记录。父 Agent 无需读取子 Session，也不增加总体报告、控制工件或第二份原生回执。

原报告和执行事实保持真实；中断通知说明已完成内容、未完成任务和可复用工作区。没有 WorkRequest 总报告或控制工件。运行中输入在最终模型回复期间到达，也必须先处理，再提交 Run 完成。输入发布与最终提交共享短发布边界；完成检查期间的输入使当前完成候选延后，已经冻结的候选意见仍留在目录中，之后的新候选按独立完成快照登记，最终只接受当前一份意见并形成一份最终报告。

### 进程意外终止后的恢复保证

运行时先保存原生调用，再记录正在执行的 call ID，随后保存结果回执。批准操作的匹配说明与 call ID 一起保存在回合的 `executing_user_comment`，回执保存后清除；执行中崩溃后，原说明仍附回原调用的未知结果回执，不重放操作或重新授权。该字段是恢复元数据，不是新控制流程或长期任务需求。普通中断调用结果未知时不重放，批次尾部未开始项明确 not_executed；已完成项保留。合法的待批准操作优先按其原调用恢复，不被普通中断清理误取消。终态与原始 AgentResult 一起保存；结果交回前中断，重启仍返回原结果，不重新调用模型或工具。

控制交接按 source Session、原始 turn 与 native call ID 定位，防止不同 Session 重用供应商 call ID 时串线。先保存直接控制事实再交给 Orchestrator；重复接收只确认同一请求，不创建新问题或新 WorkRequest。Accepted 回执完成后不再回写为工作完成；完成与取消通过第三部分通知及第四部分真实工件导航呈现。

工件登记先分配统一 UUID 并保存恢复记录，再冻结和登记；可续接的原交付恢复使用相同 ID 和字节。Scientific 返回产物后，Session 保存实际授权 ID 和唯一回执，再确认清理 Run 中待接收登记；确认中断只补确认，不重写回执。只分配身份但未冻结的网络调用不能自动重发，保留中断回执并清理未完成分配；已冻结文件损坏则报错，不能当作未产生材料跳过。初始化导入先保存声明和进度，恢复先补完导入再调用模型。Compiler 路由后固定代码建立的任务图先落盘，再冻结任务要求，接收中断不重新编译。

RunStore 和 SessionStore 分别原子保存快照，不构成跨存储事务，也不保证网络请求或命令恰好执行一次。授权内冻结登记可恢复，不等于可以安全重放所有外部操作。schema 29.0 明确拒绝旧 Run/Session，包括 28.0，不迁移或兼容；旧证据原样保留。

## 9. 如何核对模型实际看到的内容

先查原始请求与工具回执，再查 full trace 中真实 `messages + tools`，最后查模型动作和交付物。目录完整不证明模型读取，读取记录不证明理解，最终 completed 不代替逐项证据。

验收应覆盖：搜索无新工件；fetch 部分成功和复用；第三部分正文不重复进入第四部分；完整目录在压缩前后不丢项；业务回答累计、批准及说明隔离；原调用配对；编译零 Task 失败和任务失败报告；登记/接收中断后的同身份恢复。工具上下文基础检查见 [schema 25 测试计划](../history/reviews/TOOL_CONTEXT_IMPLEMENTATION_TEST_PLAN_2026-10-11.md)，前轮权限说明、CLI 与提示词检查见 [schema 26 测试计划](../history/reviews/PERMISSION_FEEDBACK_TEST_PLAN_2026-10-12.md)。
