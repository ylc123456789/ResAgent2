## 1. 改动目的与核心边界

让模型得到清楚的任务、有效的工具结果，以及始终可发现、可重读的已获取材料。减少正文重复和不可压缩目录的无意义增长，不以改架构本身为目标。

“不可损失”指该部分的内容必须完整进入当前模型输入，不只是系统还保存着原始记录。第三部分可以通过压缩从模型输入中移除精确旧内容，原始事件仍保留；第一、第二、第四部分不能以摘要、相关性筛选或截断方式省掉内容。

搜索负责发现线索，fetch 负责主动获取并登记材料。模型选择 fetch，表示认为材料值得获取和保留，不等于已读全文、认可质量或证实结论。既有用户导入和 Agent 工作交付继续登记工件；不增加“候选→采用→正式”的生命周期。

架构保持 Scientific / Compiler / Interpreter / Coding / Experiment 的现有分工，Agent 仍使用共享循环和原生 function call。权限、预算、调度、身份和冻结由固定代码负责；材料相关性和下一步行动由 LLM 判断。

## 2. 所有 Agent 的四部分上下文

| 部分 | 内容 | 维护规则 |
| --- | --- | --- |
| 1. 固定契约 | Agent 身份、系统规则、实际启用工具的说明和 schema | 同一 Session 固定，不含随运行变化的状态。不同 Agent / 新 Session 可以不同。 |
| 2. 任务需求 | 本次初始任务输入，以及本作用域累计的业务问题原文和用户回答 | 运行时从保存的事实完整构造；不由模型摘要、挑选或改写。权限批准不进入这里。 |
| 3. 工具交互历史 | 原生 assistant/tool 调用和直接回执；搜索结果、读取正文、命令输出、执行失败和完成校验反馈 | 主要可变内容，唯一可压缩部分。原始事件保存，模型输入用历史摘要和近期完整回合。 |
| 4. 完整工件索引 | 当前 Agent 授权范围内的全部已登记工件，每个 ID 一条导航记录；材料按内容分类，工作产物按 WorkRequest → Task → 工件组织；工作/任务组带真实终态和必要失败原因 | 每轮完整构造，所有分组和条目直接展开。不含报告正文、读取工作集或独立运行状态栏；无产物的终态工作/任务仍有真实结果导航。 |

这是逻辑组成，不强制等同于四条 API 消息。固定角色规则放入稳定 system，工具 schema 使用原生 tools 参数；任务和目录使用原生协议允许的消息位置；不得将一条工具调用和其回执拆开。

第二、第四部分“重建”只是从事实生成完整视图，不是压缩。第三部分读取过的正文不再复制到第四部分。历史压缩后正文可以不再可见，但工件 ID、类型和必要来源仍在目录中，可通过 read_artifact 重读。

固定契约使用同一份 Agent 身份/规则与真实工具 schema，Session 创建时保存其规范化指纹；恢复时先核对指纹与既有模型协议身份，不一致明确拒绝在该 Session 继续。工具/schema 改变后使用新 Session，不能在旧历史里静默换契约。密钥值不进入指纹，正常密钥轮换不改变契约。不新增配置恢复平台。

第二部分的“完整业务问答”保存系统实际接收的结构：问题 text、requested_fields、options 及用户 values，附问题身份和真实作用域。按已记录顺序累计，不只保留回答文字或最后一条；不声称拥有 CLI 从未采集的原始输入文本。初始任务中的结构化控制事实也保持原意，不把系统观察伪装成用户需求。

### 2.1 现有状态和反馈迁移到哪里

- 初始完成要求、可用输入、工作区/授权等本次调用必需事实属于原始任务输入，保留结构化控制字段及原始含义；Scientific 的结论要求、数据集声明，以及执行 Agent 的工作区、输出目录、权限和验收要求明确进入第二部分的初始任务框架，不引入另一个自然语言任务摘要。
- 环境检查、准备环境、执行命令、文件修改等变化在对应工具回执里给出。不能继续把同一信息另组装成第四部分工作集。
- finish 在本地 completion_check 完成后才写该调用的唯一最终回执，包含接受/拒绝及具体原因；不先保存 proposed 回执再覆盖，也不补第二条 tool 消息。本地可纠正拒绝进入第三部分，替换原 runtime_feedback 上下文段。Controller/Scheduler 的外部最终登记/交付 gate 仍是独立权威校验；其终态拒绝保存在 Run/结果里，不伪称都会自动回到模型内纠错。
- 预算、调度、授权、绑定环境和暂停位置仍由运行时保存。模型需要复查当前事实时通过现有检查/读取工具取得；逐项补齐现有工具的必要返回，不为此新增通用状态管理平台。
- 下游详细结果在对应 Task 下的原始报告工件中提供；真实终态、未执行事实和必要失败原因作为工作/任务分组的导航字段。没有生成 Task 的工作失败也必须可见，不为此新建总体报告或独立状态栏。

变化后的环境事实由 prepare_environment、run_setup、audit_env 回执提供，audit_env 明确返回当前绑定身份。Coding 的文件修改和验证回执提供验证适用的版本/是否已因修改失效；模型需要复查时，由现有 git_diff 回执补充当前验证有效性。该事实在 Agent 组装/共享回执接入层使用现有派生函数生成，capabilities 不反向依赖 Coding，不新增状态查询工具或管理器。内部完成校验仍使用真实状态，历史中的旧 PASS 不构成当前验证有效。

### 2.2 压缩和容量

保留现有按完整原生回合压缩的机制，但输入范围只覆盖第三部分。摘要可以保存研究进展、重要工具观察、决策和未解决事项；摘要本身仍属于第三部分。不能把正文或摘要复制到第二、第四部分来规避压缩规则。

先计算固定契约、完整任务需求、完整工件目录和工具 schema 的容量，再给第三部分分配可用空间；第三部分过长时压缩较早完整回合、保留近期必要完整回合。保存的原事件不删除，调用/回执配对不破坏。

近期历史保留目标和摘要目标按第三部分实际剩余容量计算，不能继续按总窗口的固定比例保留过多旧回合。最新完整回合保留，不拆调用对。以最终原生请求的完整序列化核算容量；摘要生成失败时不推进压缩边界，摘要请求仍计入现有 Run 唯一预算。

压缩后第一、第二、第四部分及最小合法历史仍放不下时，沿现有 `ContextBudgetExceeded` 明确失败；不静默省略目录或业务回答。不加入无限上下文、自动删除工件或自动改变任务范围机制。搜索不登记工件减少的是目录增长，不承诺目录永远不会超限。

## 3. 工具的统一行为

| 工具情况 | 第三部分 | 第四部分 |
| --- | --- | --- |
| 搜索网页/文献：直接返回，不产工件 | 候选结果、来源、摘要、获取标识、partial/失败事实及后续搜索提示 | 不变 |
| read_file/read_artifact：直接返回，不产工件 | 指定范围正文、实际读取范围、续读位置和错误 | 不变 |
| web_fetch/文献 fetch：直接返回，产生材料工件 | 获取说明、新增或复用的工件 ID、失败和局限 | 并入实际获取的材料 |
| request_work：延迟完成，有执行时产生报告/交付工件 | 立即接收回执和 work_request_id（对应第四部分工作组） | 终态后各 Task 下完整列出其原始报告和实际交付物；零 Task 失败仍显示工作组真实终态/原因 |
| 模型主动 ask_user：延迟回答，不产工件 | 问题已提出的回执和问题 ID | 不变；业务回答进入第二部分 |
| 权限批准：运行时执行闸门，不产工件 | 原操作最终的批准后执行结果或拒绝回执 | 不变；批准不进入第二部分 |

产生工件的工具向共享接入点提交本次实际登记的 Ref 增量；共享接入点更新可见目录。没有工件的工具不更新目录。直接模型回执给必要内容和可读 ID；登记身份、URI/hash 等权威数据由系统保存，不重复全量暴露给模型。

不建立“工具名 index”文件、独立调用结果组表或全局候选库。第四部分 WorkRequest/Task 分组直接由真实请求、任务与工件归属构造，不另存一份分组快照。工具控制交接通过公共契约传递必要控制载荷，不能继续借 question/work_request 工件作为暂停控制总线。

### 3.1 接收、登记和回执的持久边界

SessionStore 与 RunStore 是两个独立快照存储，不能把两次保存宣称成一个原子事务。使用现有状态和公共交接契约处理中断，不引入持久消息队列：

- ask_user/request_work 及运行时权限询问的固定控制载荷、问题/请求身份先在发起 Session 保存。ask_user/request_work 形成唯一接收回执，权限询问则保持原操作暂挂、不先写 tool 接收回执；公共交接结果直接传递同一载荷。Controller/Scheduler 按发起 Session、原始历史回合序号和 native call ID 幂等接收，不在接收端再分配另一个问题/请求 ID。
- Session 已保存但 Run 尚未接收时，恢复重交该已保存载荷；Run 已接收但交接确认未完成时，返回既有接收结果。两种情况都不能重新调用模型、增加调用预算、生成新 ID 或第二条 tool 回执。业务操作的后续工作和 CLI 待答问题在 Run 接收保存后才启动/呈现。
- 实际材料已登记到 Run，但工具回执/授权接入尚未保存到 Session 时，保留原调用及输出位置对应的登记结果，直到 Session 确认回执已落盘。恢复由既有端口返回这些结果，沿原 ID 补齐可见目录和唯一匹配回执。无法重建完整执行结果时，明确报告中断及已登记材料；不伪造成功，也不自动重做网络/命令等不确定副作用。
- 普通搜索、读取和命令的未持久结果沿现有中断规则处理；没有实际登记材料时不凭空补工件。第三部分的原生配对在下一次模型调用前必须完整。

已有 native call ID 只需在所属回合内唯一，因此恢复身份同时包含稳定的原始回合位置，不能假定提供方的 call ID 在全 Run 永不重复。压缩不删除原回合，不改变其恢复身份。

## 4. 搜索与 fetch

### 4.1 联网搜索和文献检索

`web_search`、`literature_search` 都不注册搜索结果工件，不为每个命中自动注册论文或网页工件。成功、空结果、partial 和失败都只形成真实工具回执；原始请求和回执仍按既有 Session/trace 规则保存，不承诺所有旧搜索结果始终进入模型输入。

返回候选包含可继续获取的稳定标识：网页 URL；论文 DOI、明确版本 arXiv ID、供应商标识和来源地址等已有可信来源字段。文献候选另给可直接复制到 fetch 的 `fetch_source`，用明确命名空间区分来源，不让模型拼装或运行时猜测。保留摘要与全文的区别、提供方、查询、后续页参数及失败原因。partial 的有效来源仍保留，其他已验收错误分类不退回“吞掉结果”行为。

工具说明明确：搜索结果仅是线索，第三部分压缩后可能不再可见；要长期保留和后续引用，应调用 fetch；需要精确正文必须读取；fetch 后目录保留的是可读取材料入口，非全文常驻。

现有网页 `max_results` 只裁剪预览、剩余结果靠工件读取的含义不再成立。修改时从公开工具、后端接口及调用链删除这条隐藏余项链和误导参数：DeepSeek 仍使用已验收短提示和单次请求，当前响应中全部有效去重来源直接进入回执，不新增候选数量裁剪。摘要沿现有字段边界（网页 snippet 最多 2000 字符），有字段裁剪明确标记；URL/获取标识不能截成不可用值。HTTP 响应继续受现有传输字节上限约束；最新完整回执连同必需上下文确实放不下时明确报容量错误，不静默省掉尾部来源，也不提示读取不存在的搜索工件。文献检索保留提供方可支持的单页大小和 next_request，这不是另一份工件索引。

搜索原始审计记录属于 Session/trace，可按原私有边界保存；不因为需要审计就重新登记为模型目录中的正式工件，也不新建搜索缓存/隐式复取通道。

### 4.2 网页获取

保留 `web_fetch(url)`，取得实际 HTML/text 并转换后冻结为 web_page，返回可读工件 ID。继续使用已验收的 markdownify/html.parser、HTTP 公共地址边界、响应限制、source_url/final_url 和代码块保真规则，不扩展浏览器或 JS 执行能力。

失败没有实际材料时只返回失败事实，不为了记录失败创建材料工件。获取成功后读取仍调用 read_artifact；read 不自动联网或隐式 fetch。

稳定冻结正文中移除本次 `Fetched at` 动态行；首次获取时间保存在原 Ref 元信息，本次获取时间保存在当前工具回执/原事件。重复获取比较同 kind、稳定冻结字节 hash、source_url/final_url 及影响正文的解析器/版本信息，不能比较整个 metadata。复用原 Ref 时不改其首次获取时间、producer 或其他冻结事实；本次真实请求仍有独立审计记录。

### 4.3 文献获取

将现有 `fetch_literature_fulltext(paper_artifact_id)` 替换成一条 `fetch_literature(source)` 主线；删除旧工具名、输入和装配，不留兼容别名。`source` 使用一个明确命名空间的来源串，例如 `arxiv:2305.12345v2`、`doi:10.xxxx/yyy`、`openalex:W…`，搜索直接提供可用值；已授权导入的论文使用 `artifact:<工件ID>`。一次输入只指定一种来源，解析按声明的来源类型进行，不靠裸字符串猜来源，也不依赖搜索自动登记。

复用现有 arXiv/OpenAlex 元信息、PDF 下载和提取组件完成来源解析；不能让模型任填一个 PDF URL 绕过当前网络边界。只支持实际已有提供方可解析的来源，不新增开放式全网站论文识别器。

现有 backends 主要提供搜索，修改时补齐这两家提供方的小型定点元信息解析：arXiv 按明确 ID 获取，DOI/OpenAlex 按提供方的精确作品身份获取；共享现有 HTTP、限速、解析和错误分类。禁止用模糊标题搜索猜是哪篇。返回身份须与请求相符；无版本 arXiv 输入先解析实际版本并在回执/Ref 明示，不与另一个明确版本合并。`artifact:<ID>` 明确只接受当前授权的 literature_paper，沿其真实关联使用已有导入 PDF；其他类型明确拒绝，不扩成通用二进制转换器。

fetch 主动获取并登记真实材料：文献元信息及来源、已取得原始 PDF、已提取全文。三者按既有材料类型独立冻结，分别提供 ID 和明确关系。没有可取得 PDF 时可保留已获取的元信息，回执如实标为 unavailable/partial；元信息解析失败则不生成假材料。PDF 已获取但提取失败时保留 PDF 并说明失败，不能声称全文已取得。

用户导入的题录和 PDF 继续可用；fetch 可利用授权既有材料提取全文。保留页码、OCR 关闭、公式/图表提取局限和来源链，不再要求用户先经过一次搜索。主动保存文献元信息属于 fetch 获取的材料，不是搜索恢复自动登记。

## 5. 一份完整索引、材料复用与统一 ID

### 5.1 目录形状

统一使用 `ArtifactIndexEntry` 作为导航条目，不再保留 `ResearchArtifactEntry` / `ResearchIndexGroup` / 全局 `ResearchIndex` 快照。目录每个真实工件 ID 一条。**一份完整索引可以在展示上分组：材料按内容分类，工作产物按 WorkRequest → Task → 具体工件组织。** WorkRequest 是主 Agent 发出的工作需求，Task 是该请求经 Compiler 拆出的具体任务，两者不能混称。全部层次直接展开；不新增索引工件、独立分组快照或 `index_artifact_id` 指向另一份目录。

最小条目保留工件 ID、kind、media_type、简短内容说明、存在的 output_name，以及必要来源/工作归属。现有归属、Attempt 和来源字段沿真实记录生成，不能改写 producer，也不能把多个引用关联误当多个生产者。不新增可变标签、相关性分数、采用状态或独立资源树存储。

示意：

| 类型 | 工件 ID | 内容说明 | 关联 |
| --- | --- | --- | --- |
| 文献 | p1 | 已获取元信息和摘要 | 稳定论文来源 |
| 文献 | pdf1 | 原始 PDF | source=p1 |
| 文献 | text1 | 提取全文 | source=pdf1 |
| 网页 | page1 | 官方页面正文 | source_url/final_url |
| 工作交付 | report1 | Task 原始执行报告 | work_1 / 实际 Task、Attempt |
| 工作交付 | result1 | 对照结果 | work_1 / 实际 Task、Attempt |

上表没有搜索结果清单条目。模型可直接读取 text1、report1、result1；来源关系不构成必须先打开的子索引。

“直接可读”指无需打开子索引即可定位实际工件，不代表 read_artifact 可以解码任意二进制。该工具仍只读 UTF-8 文本。PDF/模型等二进制工件完整列出并保留类型；PDF 正文通过 fetch_literature 使用已授权题录及其关联 PDF 提取为全文工件后再读，不新增隐式转换或自动 fetch。

材料按已有 kind 对应的内容用途排列，同类内保持首次接入顺序；工作组按 WorkRequest 请求顺序排列，组内按现有工作流任务顺序排列 Task，每个 Task 先列全部原始报告（按 Attempt 号），再列其他工件（按首次接入顺序）。分类、工作标题和任务分组都是共用目录 builder 从真实归属生成的完整视图，不另存分类表或分组快照。未知但合法类型、没有 WorkRequest 归属的其他产出也必须列出，不允许因分类遗漏。工具/调用时间作为来源属性，动作流水由第三部分及原事件负责。

#### 工作产出的导航信息

前面的简表只示意条目内容，不代替下述工作分组，也不作为实际信息量标准。工作产出必须让模型知道“这项工作要解决什么、哪份文件包含什么、哪次执行产生、需要深入时读哪份原件”，不能只显示“代码/结果＋ID”。

- 外层按 Scientific 发出的 WorkRequest 分组，以既有 work_request_id 为稳定定位键，显示原始 WorkRequest.objective；内层按真实 WorkflowTask 分组，以现有 task_id 为定位键，再直接展开该任务实际交回、已登记且授权的全部产物。同一 WorkRequest 中不同 Task 的产物不得混为一份平铺清单。主 Agent 仍只提交工作需求，不负责预先选择 Task 或具体实施；返回时任务分组帮助它理解和查找已有结果。
- 第三部分 request_work 接收回执中的 work_request_id 直接定位第四部分同名工作组，无需再生成 work_result_index_id。工作标题显示一次目标，不在每条工件里重复；工作组不是一份需要另行读取的文件，不另存分组快照。
- 每个工件保留 ID、kind/media_type、实际内容说明和存在的 output_name。内容说明沿生产者的 summary，说明文件包含什么及用途，例如“校准/测试集指标对照与指标定义”，不能仅写“实验结果文件”。生产工具/finish 的说明与测试同步这一要求，不新增一次模型总结。
- 任务行显示真实 task_id 与执行 Agent 类型，不新增一次模型总结或假设 WorkflowTask 已有独立 title 字段；任务内工件继续提供用途说明。工件另展示真实 Attempt 号及该 Attempt 的状态，不再为 Attempt 增加第四层导航。来源/派生关系只取实际记录。相同 output_name 的不同 Attempt 必须能区分，旧失败 Attempt 不能随任务最终成功被标成成功。
- 各 Task 下挂真实原始报告，不再生成总体工作简报或复制所有 Task 报告的整体 WorkRecord 工件。重试后的不同终态 Attempt 各有报告，不覆盖早期报告，也不另造 Task 聚合报告。没有实际执行 Attempt 的 blocked Task 显示真实原因和“未执行”，不制造 Agent 报告；编译拒绝等没有 Task 的终态工作组显示状态、原因和“未创建任务”，不造占位工件。
- 原工作目标说明、逐工件内容说明和来源身份是导航；详细 Task instruction、Attempt report、错误详情和指标正文保存在对应报告/交付工件及原始 Run/Session 中，报告原件按需读取，不复制进第四部分。执行状态只说明执行事实，不代表材料已经独立复核或科学结论成立。
- 同一工件被后续任务/工作作为输入复用时，仍留在原生产 WorkRequest/Task 或原材料分类下，补充真实引用关系；不能在每项任务下面重复放一份，也不能改写成新任务的产出。初始输入与主 Agent fetch 的材料不因被子 Agent 使用就复制进工作产物组。工作组的“全部工件”是该工作的实际交回产物，不是工作区所有临时文件或使用过的全部输入。

第三部分回执与第四部分工作组的对应示意（ID 为示意名，所有已登记工件均直接可定位）：

  status：accepted

模型从第三部分的 work_1 找到第四部分对应组后，能直接看到全部任务分组和工件，可选择 result_1 查看对照，选择 pred_1 做复算，或读取相关 Task 原始报告了解结果；不要求先打开报告或子索引才能发现其他 ID。工作产物在展示上是“WorkRequest → Task → 工件”三层，仍只有一份完整目录。工作说明和条目都由真实 WorkRequest、Task、Attempt、Ref 及授权接入关系确定性构造，删除旧 ResearchIndexGroup 时必须保留原有工作目的的导航价值。无工件的终态组是实际工作/任务的结果导航，不是正式工件或另一个状态平台。

### 5.2 材料去重与目录唯一性

1. **搜索内部：**本次响应中重复命中按已有可靠标识去重。网页保留精确 URL 规则，不粗暴去掉查询参数；文献使用稳定标识，明确 arXiv 版本不得合并。不引入标题相似度自动合并。
2. **fetch/登记入口：**在当前授权范围查询已有同类材料。文献可复用明确身份及对应既有冻结来源；网页新 fetch 仍实际获取后比较内容。相同材料快照和必要来源一致时复用已有 ID，正文、元信息、版本或来源有实质差异时保留独立工件。hash 只是内容一致的证据，不单独替代来源身份。获取时间、调用 ID 等本次观察与真实来源分开保存，不能为了去重丢掉本次请求事实。复用现有冻结、校验、来源边界和领域小函数，不保留旧 hash 派生 ID 逻辑，不新增 ResourceManager。

**完整索引不再另做一层材料去重。** 它以 artifact_id 为唯一键接入授权输入与实际工具/工作交付，再按材料类型和真实工作归属组织。多个入口可以引用同一工件，但只补充真实引用关联，不创建第二条目录记录；重复接入不能改变原 producer 或冻结事实。同一 ID 对应冲突 Ref 时明确拒绝，不能用后到记录覆盖前一条。不同真实快照不因 URL/标题一样被目录隐藏。组织规则决定条目放在哪里，唯一键决定它只有一条，两者不冲突。

重复搜索不修改既有工件；没有全局候选目录。重复 fetch 不承诺天然省掉网络请求，只有符合当前明确缓存/复用条件时才复用原件。

### 5.3 统一工件 ID，与内容 hash 分离

**直接替换现有 ID 生成机制：所有工件使用与内容无关的随机 ID，SHA256 仅负责冻结内容校验及材料复用比较。** 不保留“普通工件内容 ID＋未来工件临时 ID”两套算法，也不增加临时 ID 到最终 ID 的映射。

源码基线中的 `_artifact_id(category, identity)` 将登记身份序列化后做 SHA256：任务交付使用 Task/Attempt/输出序号，导入使用内容及元信息，Scientific 材料使用 Session/内容/说明，系统材料使用种类/作用域/内容，最终报告使用 Run。它们并非全部仅按正文计算，但都要一起替换；不能只给 WorkRequest 另加一个例外。

在 contracts 已有 identifiers 模块放置唯一纯 ID 生成函数，使用 Python 标准库，不新增依赖。所有登记入口使用同一函数，避免跨包放置身份逻辑而造成反向依赖：

```python
def new_artifact_id() -> ArtifactId:
    return f"artifact_{uuid4().hex}"
```

所有新工件都通过这个函数取得同一格式的 ID。ID 不表达类型、内容、顺序或来源；类型和来源由 Ref 表达，目录顺序使用首次接入顺序。问题 ID、工作请求 ID、原生调用 ID 继续表示各自控制对象，不冒充工件 ID。问题/工作请求在发起端使用各自前缀的 UUID 控制身份，并按第 3.1 节持久交接；不从接收列表长度推导恢复身份。

实际需要新增工件时分配，在冻结前保存分配身份；冻结和登记直接使用该 ID，内容完成后不重新生成 ID。WorkRequest 发起时只保存工作请求身份，不提前分配未来报告 ID。识别可复用材料时直接返回已有 Ref/ID，不创建一个新 ID 再做别名。新快照使用新 ID，不覆盖旧快照。

**恢复规则必须一起改，不能只把函数换成 uuid4。** 现有任务/最终报告登记利用可重算 ID 处理“文件已冻结、Ref 尚未保存”的崩溃。新机制在写冻结文件前持久保存已分配 ID：

- 实际材料登记共用 Run 内一个未完成登记字段，保存原逻辑操作及输出位置、已分配 ID，以及已有内容的预期 hash、必要归属和冻结位置。逻辑操作使用已有调用/请求/Task/Attempt 的身份；没有模型调用的导入和最终报告使用既有输入位置或最终产物位置。它是短暂恢复状态，不是另一份工件索引，不保存第二份正文，也不维护永久“资源标识→工件 ID”表。
- 持久保存登记事实后按同一 ID 原子冻结；将正式 Ref 加入 `Run.artifacts`、接入 Run 所属结果记录，在同一次 Run 保存中提交。结果也需交回 Session 的登记，保留原调用与登记结果关联到第 3.1 节的回执确认完成后再清除；Run 独有的导入/最终报告等在自身提交完成后清除。沿用现有 RunStore 原子快照与冻结实现，不新增独立事务平台。
- 恢复时若登记尚未完成，沿已保存 ID 继续；已冻结文件符合预期则直接完成登记，不重新读取后来变化的工作区文件代替原快照。尚未冻结且原内容无法取得时明确失败，不声称存在材料。已经提交的登记沿所属结果记录恢复原 Ref，不再分配 ID。
- 同 ID、同一冻结事实的重入返回原 Ref；同 ID 对应不同内容或冲突归属明确报错，不覆盖、不悄悄另分配 ID。新的一次工具调用与旧调用恢复要区分，不能把“网络/命令已执行过”与“材料登记完成”混为一谈。

导入、Scientific 材料、Task 原始报告/交付、系统材料和最终科学报告使用同一分配、冻结、提交规则；入口只保留各自必要的来源与权限校验。调用方不能让 LLM 指定或覆盖待生成工件 ID。删除旧 `_artifact_id` 及各入口的 hash 派生身份假设，保留内容 SHA256 和来源校验；schema 25 拒绝旧恢复，不加旧 ID 解析、重定向或兼容层。

创建 Run 的初始化也按此规则执行：先保存初始任务、原始导入声明及初始化进度，再逐件分配/保存 ID、冻结输入。尚未完成初始化不能启动模型。中断后由恢复入口沿已保存输入位置和 ID 补齐；来源不可取得时明确失败，不能仅因为 Run 文件已经存在就无法继续，也不能跳过尚未导入的输入。暂停期间追加导入使用相同规则。

### 5.4 底层权威和范围

`Run.artifacts` 及冻结文件继续负责权威身份、内容 hash、归属和读取校验；磁盘按 ID 保存，不改成物理分类树。第四部分从当前授权输入与实际已登记返回 Ref 构造，Session 仅保留已授权接入 ID/必要关联，不另建第二份完整工件元信息真相源。

当前 Agent 的完整可见工件集合明确为：**当前请求授权输入 ∪ 本 Session 实际登记并接入的工具产出 ∪ WorkResult 明确交回的 Task 原始报告/交付物**。所有 ID 解析到 Run 的权威 Ref；从持久授权接入事实重建，不能只依赖一个可丢失的 memory 列表，也不能以 producer=Scientific 查询整个 Run 代替授权。WorkResult 给的是本次实际交回增量及工作/任务的结果导航事实，不是另一份全局目录；无产物的终态导航来自当前 Agent 已接收请求的真实结果，不扩展工件读取权限。

Scientific、Coding、Experiment 使用同一构造和合并规则，但各自授权范围不同。目录中出现条目不能扩权；相同资源在其他作用域存在，不代表本 Agent 可以读取或复用它。初始导入、工作交付及其他既有正式证据工件仍完整列出。

question、answer、work_request 和 research_index 不再新建正式工件：问题、回答、请求等控制事实落在既有 Run/Session 状态中；ResearchIndex 生产、读取及分组快照链一并移除。总体 WorkRequest 简报和重复聚合各 Task 报告的 work_record/work_feedback 工件链一并取消，原任务图、Attempt、报告、错误和控制事件仍保存于 Run/Session。Task 原始报告、正式验收/测量记录和实际交付继续作为材料保留，不能为减少条目而把有用原件藏掉；最终科学报告不属于取消的总体工作报告。

## 6. WorkRequest：提前返回工作引用，按 Task 交回原始报告

**发起端在返回接收回执前分配并保存 work_request_id；回执只需要 accepted 和该工作 ID。** 它同时用于运行控制和定位第四部分同名工作组，不是工件 ID，不能传给 read_artifact。不新增工作索引 ID，不预分配总体简报或未来 Task 报告 ID。

```text
Scientific 调用 request_work
→ 在 Session 保存稳定的 work_request_id 和原始请求
→ 原生回执：accepted + work_request_id
→ Controller 幂等接收并保存到 Run
→ Scientific 暂停，Compiler 拆出实际 Task
→ Scheduler / Coding / Experiment 执行任务
→ 在每次 Attempt 终态裁定后登记原始报告和实际产物
→ Interpreter 保真组织 WorkResult 的任务结果及实际工件引用
→ Controller 接入第四部分同名 WorkRequest / Task 分组
→ Scientific 恢复，按目录 ID 读取相关 Task 报告或具体产物
```

上述接收载荷先保存于发起 Session，再按第 3.1 节交接到 Run。“延迟”表示先回接收结果、暂停本 Agent、终态后恢复，不增加主 Agent 与子 Agent 同时继续工作的并发模式。主 Agent 恢复前须保存真实工作结果并完成其报告/产物的授权接入，下一次模型输入直接包含完整对应工作组；原 accepted 回执保持不变。

### 6.1 Task 报告的真实来源和登记时机

当前基线中 AgentResult.report 主要保存到 Attempt.report，再复制进整体 WorkRecord；并不是每个 Task 已有独立报告工件。修改时沿既有 module_report 类型和统一登记入口，将**每个真实终态 Attempt 的原始报告冻结一次**，挂在真实 Task 下。不额外调用 LLM，不让子 Agent 再交一份内容相同的简报，也不再为所有 Attempt 生成 Task 聚合报告。现有 build_module_report 是可选择内容并自动换行的投影，不能不加调整就当原始报告保存；报告包装保留 report 原字符，不筛选、不强制插行，长行沿共享字符窗口读取。旧 helper 改为这条唯一保存路径或删除，不保留平行报告机制。

报告保留子 Agent 原始 report，附实际任务、Attempt、最终状态、error、warnings 及相关输出身份。接收校验/交付登记等系统失败另以真实诊断事实记录，不能替换原 report 或假称 Agent 已认可失败结论。若使用 Task 累计 warnings，明确这是累计范围，不能冒充本次 Attempt 独有警告。预执行检查失败的报告标明运行时来源和“Agent 未启动”；依赖阻塞且从无 Attempt 的任务只显示真实未执行状态和原因，不伪造 Agent 报告。

先完成外部结果/交付校验并确定 Attempt 真实终态，再冻结报告；不能先登记成功报告，之后把该 Attempt 改判失败却留下失真的冻结原件。报告按第 5.3 节保存分配 ID、冻结、提交及恢复；登记中断必须先补齐结果材料，不能带着缺失报告恢复主 Agent。报告引用实际业务输出，不把自身 ID 放进自身输出清单。

等待用户问答或操作批准的 Attempt 尚未终态，不为每次暂停生成 Task 报告。重试形成新的 Attempt，报告独立冻结；早期失败报告仍完整展示，状态不会被后来的成功覆盖。暂停恢复继续同一 Attempt，重复接收不生成第二份报告。

### 6.2 零 Task、零交付与工作失败

WorkRequest 和 Task 分组可以带真实终态、错误类别/原因及未执行事实，即使没有实际工件也展示终态导航。它们不是空工件，不写占位文件，不另建运行状态栏。编译失败显示“未创建任务”；依赖阻塞显示“任务未执行”；有 Attempt 但没有业务交付时仍保留该次真实报告。不新增总体 WorkRequest 报告来包这些情况。

当前编译拒绝等路径直接终止 Run，不会恢复 Scientific；新方案必须落实失败交接。在 Run 仍允许模型继续、失败可作为工作结果反馈时，保存该 WorkRequest 真实失败并沿同一 WorkResult 交回，让 Scientific 从第四部分看到终态并决定下一步。零 Task 失败不伪造任务、报告或工作流版本。Run 本身因预算、截止、外部中断或不可恢复存储问题已经不能继续时，保存真实终态并按原终止边界退出，不声称模型已经收到结果。

### 6.3 Interpreter 和控制结果

Compiler 仍负责把需求转换为任务，Interpreter 仍无状态地保真组织反向交接；删除其总体说明拼接，不改成模型二次总结。原始任务图、Attempt、报告和控制事件仍以 Run/Session 为权威保存，不复制成整体 WorkRecord 工件。

将 WorkFeedback 收敛为 WorkResult：传递稳定工作身份、真实工作/任务结果、已登记 Task 报告和交付 Ref 增量；不携带总体报告正文，也不引用 ResearchIndex 快照。WorkResult 不是新工件、不是第二份全局目录。删除旧 work_record/work_feedback 工件交接链及已无消费者的整体报告 helper；现有 Agent 的自然语言 report 加控制字段接口保持。

旧 accepted 回执不改写，不为同一原生调用追加第二条无配对 tool 消息，不把 Task 报告正文自动注入上下文。第四部分完整导航更新后，正文由模型通过 read_artifact 读入第三部分。

## 7. ask_user 与权限批准

### 7.1 模型主动业务提问

调用 ask_user 时，保存问题与问题 ID，形成“已提出问题”的唯一原生回执，然后暂停。用户回答到达后校验问题、作用域及字段，持久保存完整原题/原答案；当前作用域的业务问答完整累计进入第二部分，再恢复模型。

question/answer 不再登记工件，不进入第四部分。当前 P1 修复的作用域隔离和恢复语义保持：同一逻辑任务的业务补充不能因为恢复失败就丢掉；批准不跨 Attempt 自动沿用。CLI 的答复、show 和审计从真实问答状态读取，不依赖 question/answer 工件文件。不能因去掉工件就去掉持久性或来源校验。

### 7.2 运行时操作批准

继续共用用户提问、暂停和回答入口；以准确动作快照区分批准与业务问题，不按 approve/yes 文本猜测。权限策略的允许/询问/拒绝范围、准确命令、参数、目录/环境/目标绑定及单次消费保持，不增加自动批准或长期许可。

批准问题是原操作的执行闸门，不伪装成模型又调用了一次 ask_user。原操作的调用在 Session 中持久暂挂；用户回答后核对同一准确动作，再执行或拒绝，形成该原操作的唯一最终 tool 回执，然后恢复模型。执行前若事实边界变化，重新检查而不是沿用不匹配批准。

暂停期间未完成调用不发送给模型；模型恢复前必须补齐唯一匹配回执。业务 ask_user/request_work 已接收并完成其工具回执，与暂挂待批准的原操作是不同语义，不能补出第二条 tool 回执。支持一次响应中多调用时，保留真实执行顺序，其余调用不能因暂停或崩溃而被重复执行。

明确保持当前批次规则：finish、ask_user、request_work 必须各自单独调用。普通多调用按顺序执行；某条操作等待批准时保留前面已执行回执，该条原调用暂挂，后面未启动的调用立即取得 not_executed 回执。回答后只继续/拒绝暂挂的那一条，补齐其最终回执；下一批动作由模型重新决定。不新增批次调度器或自动续跑尾部调用。

批准/拒绝及动作快照保存为运行记录，不进入第二或第四部分。批准不代表操作执行成功，模型看到的是最终执行结果/拒绝；真实执行留痕仍由现有操作工具记录。不承诺无法从事实判定的跨崩溃 exactly-once，沿现有中断恢复规则明确处理不确定执行。
